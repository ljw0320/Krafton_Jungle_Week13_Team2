# 리버스 프록시 첫 구현

기존 웹서버를 백엔드로 두고, 별도 단일 스레드 LT `epoll` 프로그램이 중계한다.
기존 웹서버의 keep-alive 구현은 변경하지 않는다.

## 실행

프로젝트 루트에서 빌드하고, 백엔드·프록시는 각각 다른 터미널에서 실행한다.

```bash
make all reverse_proxy

# 터미널 1: 기존 웹서버
./webserver 8081 www cgi-bin

# 터미널 2: LISTEN_PORT BACKEND_IPV4 BACKEND_PORT
./reverse_proxy 8080 127.0.0.1 8081

# 터미널 3
curl -v http://127.0.0.1:8080/
curl --data-binary 'hello' http://127.0.0.1:8080/echo
curl 'http://127.0.0.1:8080/cgi-bin/adder?a=12&b=30'
```

프록시는 모든 IPv4 인터페이스에서 수신한다. 백엔드는 실행 시 지정한 숫자
IPv4 한 개로 고정하며 요청에 따라 목적지를 바꾸지 않는다. 포트는 1~65535다.
동일 포트의 루프백 백엔드는 거부한다. 다른 로컬 인터페이스 주소로도 프록시
자신을 백엔드로 지정해서는 안 된다.

## 동작과 제한

| 항목 | 동작 |
| --- | --- |
| 경로 | 모든 경로와 쿼리 문자열 그대로 전달 |
| 메서드 | GET·POST, 그 외 405 |
| 연결 | 클라이언트 HTTP/1.1 유지, 대응 백엔드 연결도 1:1 재사용 |
| 요청 본문 | Content-Length 기준 최대 64KiB 전체 수신 후 백엔드 연결 |
| 큰 요청 | 64KiB 초과 413, chunked 요청 400 |
| 응답 | Content-Length 기반, 16KiB 본문 버퍼로 중계 |
| 본문 없는 응답 | 204·304 처리, 304의 표현 길이 헤더 보존 |
| 미지원 응답 | chunked·길이 없는 일반 응답·1xx는 502 |
| 연결·동시 처리 | 클라이언트 최대 16개, 처리 풀 8개, 초과 요청 503 |
| 백엔드 연결 | 최대 3초 |
| 백엔드 송수신 | 무진행 최대 5초 |
| 전체 처리 | 첫 요청 바이트 수신부터 마지막 응답 바이트의 소켓 전달까지 절대 10초 |

클라이언트 요청 수신과 응답 송신에도 무진행 5초를 적용한다. 첫 바이트가 없는
유휴 연결은 accept 이후 5초로 제한한다. 데이터가 진행해도 전체 기한은 연장하지
않는다. 10초에 도달하면 가능한 오류 응답을 즉시 한 번 송신 시도한 뒤 종료한다.
클라이언트 애플리케이션이 마지막 바이트를 읽은 시점까지 보장하는 기한은 아니다.

클라이언트 요청 수신 시간 초과는 408, 백엔드 시간 초과는 504, 연결 실패나
잘못된 응답은 502다. 응답 일부를 이미 보냈다면 오류 응답을 이어 붙이지 않고
연결을 종료하므로 클라이언트는 미완성 응답을 관찰할 수 있다.

## 버퍼·헤더·자원 수명

연결 16개는 작은 상태 정보만 보유하며, 실제 요청 바이트가 도착하면 처리 풀
8개 중 하나를 확보한다. 처리 공간에는 요청 최대 80KiB, 입출력 헤더,
본문 중계용 16KiB가 포함된다. 풀 고갈은 대기 없이 503 후 종료이다.
응답 완료 후 입력이 비면 풀에 반환하고, 미리 받은 다음 요청이 있으면
현재 요청 바이트만 소비한 뒤 후속 데이터를 보존해 순서대로 처리한다.
응답 크기에 비례하는 할당이나 임시 파일은 사용하지 않는다.
미전송 본문이 있으면 백엔드 읽기를 중단하고 전송 완료 후 재개한다.

클라이언트는 HTTP/1.1 기본 유지, Connection: close·HTTP/1.0·100번째 응답은
종료한다. 응답 완료 후 다음 요청까지 유휴 5초이며, 다음 요청마다 전체 10초
기한을 새로 적용한다. 프록시 자체 오류는 종료하며 유효한 백엔드 4xx/5xx는
연결 유지가 가능하다. 백엔드 응답의 Connection은 제거하고 클라이언트 정책에
맞게 재생성한다. 백엔드 연결은 HTTP/1.1 응답 경계를 모두 수신한 뒤 재사용한다.

헤더 크기는 요청·응답 각각 16KiB, 필드 개수는 512개까지다. 연결 전용 헤더와
Connection에 나열된 필드를 양방향에서 제거한다. 백엔드 요청은 HTTP/1.1로 구성하고 Host는 백엔드 IPv4:포트로 교체하고
Via를 추가한다. 나머지 헤더는 중복 필드도 보존한다. 중복 Content-Length·길이
오버플로·잘못된 바이트·미지원 전송 인코딩은 거절한다. Expect는 기존 파서처럼
417이며 선행 요청은 앞선 응답 완료 후 순차 처리한다.

종료할 응답 완료 후 SHUT_WR하고 최대 100ms 동안 남은 입력을 폐기한다. 정리 시간도
전체 10초 이내다. 초과 접속은 중계 자원 없이 별도 최대 8개 오류 전송 슬롯에서
503을 전송·정리한다. 오류 슬롯까지 포화되면 연결을 닫는다. 접속 폭주에서 모든
연결에 503 전송을 보장하지는 않는다.

## 검증

```bash
make test_proxy
```

- 헤더 단위 검사: 경로·Host·Via·Connection, 연결 전용 필드 제거, 중복 길이·오버플로·chunked·본문 없는 응답.
- 실제 백엔드: 2MiB 바이너리 파일, 64KiB POST echo, CGI, 404.
- 실제 TCP: 요청 전체 수신 후 백엔드 연결, 분할 본문, 연결 종료, 8개 상한과 회복, 연결 실패 502, 취소 후 FD 회수.
- 시간 제한: 클라이언트 수신 무진행 408, 백엔드 무진행 504, 계속 진행해도 전체 10초에 504.
- 응답 분할·느린 수신 후 재개·응답 도중 백엔드 종료.

전체 기한을 실측하므로 약 10초 이상 걸린다. 연결 3초는 로컬 정상/거절 연결 외에
패킷 폐기를 이용한 실측을 하지 않는다. HTTPS·DNS·IPv6·공유 연결 풀·chunked·
로드밸런싱·캐시·일반적인 자동 재시도·10K 부하 검증은 제외했다. GET의 제한된 재시도 정책은 아래 백엔드 keep-alive 절에 설명한다.


클라이언트 keep-alive 추가 검증: 같은 소켓의 POST+선행 GET, 유효한 404 응답 후
재사용, 100번째 응답 종료, 명시적 close 백엔드의 100개 연결 생성, 프록시 오류 뒤 후속 요청
미실행, 15개 유휴 연결의 버퍼 반환, 유휴 5초 및 HTTP/1.0 종료를 검사한다.
상태 단위 검사에서는 요청별 전체 기한 재설정·풀 상한·중복 반환을 검사한다.
수동 재사용 확인은 아래 명령의 두 번째 요청에서 Re-using 연결 로그를 확인한다.

```bash
curl --http1.1 -v http://127.0.0.1:8080/ http://127.0.0.1:8080/
```


## 백엔드 keep-alive

클라이언트별 백엔드 소켓을 최대 하나 유지한다(최대 16개). 처리 풀은 기존
8개이며 유휴 연결은 큰 버퍼를 보유하지 않는다. 응답 수신 완료부터 유휴 4초,
백엔드 연결당 100개 응답 후 정리하며 클라이언트 연결은 별도 정책으로 유지한다.
클라이언트가 종료되면 대응 백엔드 소켓도 종료한다.

HTTP/1.1 응답에서 Connection: close가 없고 선언된 본문을 모두 수신했을 때만
재사용한다. HTTP/1.0·명시적 close는 백엔드만 정리한다. 유휴 EOF·오류·예상치
않은 데이터는 해당 백엔드 연결을 폐기하며, 재사용 직전에도 MSG_PEEK으로 확인한다.

확인 직후의 종료 경합은 여전히 가능하다. 재사용 연결의 전송/수신 실패에서
GET이며 백엔드 응답 바이트를 아직 받지 않았고 클라이언트에도 응답하지 않았다면
새 연결로 최대 한 번 재시도한다. POST 전송 시도 후에는 자동 재시도하지 않는다.
응답 바이트 수신 후 실패는 재시도하지 않으며, 클라이언트 응답 전이면 502,
응답 일부 전달 후이면 연결을 종료한다. 재시도는 기존 전체 10초 기한을 유지한다.
백엔드 무진행 시간 초과는 재시도 없이 기존 504 정책을 적용한다.

검증: 기존 TCP 검사 8개와 백엔드 검사 3개, 헤더·상태 단위 검사를 실행한다.
백엔드 실제 연결 개수, 4초 후 재연결, 100개 프론트 요청, 명시적 close 및 유휴
EOF, 클라이언트 종료 시 FD 회수, GET 1회 재시도·POST 단일 실행·부분 헤더
수신 후 미재시도를 확인한다. 단위 검사에서 백엔드 100개 상한과 재시도 시
원래 요청 기한 보존도 확인한다. 공유 백엔드 풀과 10K 부하 검증은 범위 밖이다.


실행 용량은 `PROXY_CONNECTIONS`·`PROXY_CONTEXTS`로 조정한다. 기본값은 16·8이며, 자세한 FD 한도·100개 연결 검증은 루트 README의 실행 시 용량 설정 절에 있다.


## poll을 유지한 연결 관리 개선

빈 연결 슬롯은 목록에서 O(1)로 확보·반환한다. poll 감시 배열은 유지하면서
상태가 바뀐 연결의 항목만 추가·수정·제거한다. 제거 시 마지막 항목을 이동하고
소유 연결의 인덱스를 수정한다. 클라이언트 구간과 백엔드 구간은 각각 등록한다.
준비 이벤트는 콜백 실행 전에 별도로 복사하고, 슬롯 수명과 백엔드 소켓 세대로
오래된 이벤트를 무시한다. 타이머는 연결당 한 항목인 인덱스 최소 힙이며
갱신·취소 O(log N), 다음 기한 조회 O(1)이다. 만료된 연결만 처리한다.

연결 상태는 기존과 동일하며 비차단 송신을 최대 4회 이어서 시도한다.
EAGAIN 또는 같은 상태가 유지되면 poll로 돌아간다. 버퍼8개·시간 제한·GET/POST
재시도 정책·프록시와 백엔드의 keep-alive 정책은 변경하지 않는다.
poll 자체와 준비 이벤트를 찾기 위한 poll 배열 검사는 여전히 O(N)이다.
웹서버의 전체 순회·정렬 연결 목록 타이머도 이번 변경 범위 밖이다.

`make test_proxy`에 감시 배열 갱신·swap 제거·오래된 이벤트 복사본과 3000회
최소 힙 갱신/취소/순서 모델 검사를 추가했다. 기존 TCP 검사 11개도 통과했다.

`PROXY_PROFILE=1`이면 준비·poll·이벤트 탐색/처리·accept·변경 갱신·타이머의
호출 수, wall 시간과 스레드 CPU 시간을 합산해 종료 시 stderr JSON으로 출력한다.
기본값은 비활성이다. poll 대기 시간과 CPU 비용을 분리하며 연결별 로그는 없다.
update는 accept/이벤트 처리/타이머 안에서 호출되므로 해당 계측 구간과 중첩된다.
모든 구간 시간을 단순 합산하지 않는다. ready_scan_dispatch에는 실제 I/O 처리도
포함되며 순수 순회 비용만을 나타내지 않는다. slots_checked의 이전 값은 연결
슬롯 검사 수, 이후 값은 poll 항목 검사 수로 집계 단위가 달라 직접 비율로 비교하지 않는다.

```bash
python3 tests/check_capacity.py --connections 10000 --empty-body --rounds 1 --proxy-profile --output artifacts/proxy-management/proxy-after-10000.json
```

같은 설정·계측 활성 단회 결과는 루트 README에 정리했다. C10K 유지 검증은
여전히 미통과이며 poll 자체가 잔여 CPU 비용의 큰 부분이다. 이 결과는 공유
WSL의 단회 비교로 성능 개선율을 일반화하지 않는다.


## 프록시 LT epoll 전환

프록시만 Linux epoll의 레벨 트리거 방식으로 전환했다. 웹서버는 poll과 기존
타이머 구조를 유지한다. epoll_wait 한 번에 최대64개 이벤트를 받고, 이벤트별
비차단 송신 최대4회·신규 연결 수락 최대16개와 매 묶음의 타이머 검사를 유지한다.

reactor.h의 FD 배열은 등록 상태 메타데이터일 뿐 poll에 전달하거나 전체 순회하지
않는다. epoll에 등록된 준비 이벤트만 처리한다. EPOLLOUT은 연결 수립·미전송
데이터가 있을 때만 사용한다. 읽기를 멈춘 백엔드는 DEL로 감시에서 제거하고
버퍼가 비면 ADD로 복구하므로 HUP가 반복돼 CPU를 소모하는 것을 방지한다.
소켓을 닫기 전에 등록을 제거한다. 등록마다 별도 식별자를 발급해 FD 번호나
등록 슬롯이 재사용된 뒤 도착한 이벤트도 무시한다.

개별 등록·변경 실패는 원인을 출력하고 해당 연결만 정리한다. epoll_create1과
리스너 등록 실패, EINTR 이외의 epoll_wait 오류는 프록시를 실패 상태로 종료한다.
EINTR은 종료 요청이 아니라면 재대기한다. poll 자동 복귀는 없다. 32비트 등록
식별자가 소진되면 재사용해 오래된 이벤트와 충돌시키지 않고 등록을 실패 처리한다.

검증: 기존 TCP11개·헤더·상태 검사 및 실제 socketpair를 이용한 등록/변경/제거,
쓰기 감시 해제, 읽기 pause/resume·EOF, 오래된 토큰, 70개 준비 FD의 최대64개씩
처리, 개별 등록 실패 후 정상 처리, 생성 실패·대기 오류·EINTR, 최소 힙 모델
검사를 통과했다. 명령은 `make test_proxy`이다.

계측의 poll 항목은 epoll_wait로 변경했다. 동일한 연결 상한11000·버퍼8·동시성4·
빈 POST·1회 순회·계측 활성에서 1000개는 통과했다. 10000건 처리 시간은 기존
poll 29.628초에서 epoll 15.844초, 프록시 CPU 28.11초에서 2.77초로 감소했다.
그러나 확인 시점 클라이언트2987개·백엔드2365개로 동시10000개 유지는 미통과다.
기존 유휴 제한4~5초를 넘긴 상태이며, 백엔드 CPU17.9초와 실행기 CPU10.94초도
남아 있다. 프로세스 CPU 시간은 병렬이므로 합산해 wall 시간으로 해석하지 않는다.

결과는 docs/tests/proxy-epoll/epoll-1000.json·docs/tests/proxy-epoll/epoll-10000.json이다. 공유 WSL의 단회 비교이므로
일반적인 성능 개선율이나 C10K 통과를 주장하지 않는다. 다음은 웹서버 비용을
세분화해 개선하고 부하 실행기의 순회 지연도 함께 확인하는 단계다.
