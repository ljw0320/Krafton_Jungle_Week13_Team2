# 서버 직접 접속 처리량 기준 측정

## 조건

- 대상: 프록시를 거치지 않은 웹서버의 HTTP/1.1 빈 POST /echo.
- 동시 연결: 1·4·8·16·32, wrk 부하 스레드 1개 고정. 파이프라이닝 없이 각 연결에서 응답 후 다음 요청을 즉시 보낸다.
- 각 조건 워밍업 5초 후 본 측정 30초, 3회 반복. 각 반복 안에서 동시성을 오름차순으로 실행했다.
- 매 실행 서버를 새로 시작한다. 임시 문서 루트, CGI 비활성, 워커 4개·작업 큐 4개·버퍼 8개·연결 상한 11,000개 고정.
- 연결 상한 11,000개는 앞선 C10K 시험과 같은 값이며, 기본 상한 16개 때문에 동시성 32가 거절되지 않게 유지했다.
- JUNGLE_PROFILE=0. 요청 예산·버퍼 대기·keep-alive 100회 정책과 종료 규칙은 그대로다. wrk는 서버가 연결을 닫으면 재접속한다.
- 서버는 기존 Makefile 빌드(-g, 별도 -O 최적화 옵션 없음)를 사용했고 서버 소스나 설정 기본값은 변경하지 않았다.
- 실제 실행 환경은 WSL Ubuntu 18.04.6 LTS, 논리 CPU 8개다. 같은 장비에서 생성기와 서버를 실행했다. 이전 문서에 기재된 Ubuntu 24.04와 구분한다.
- wrk 4.2.0 공식 태그 소스를 artifacts/load-tools에 빌드했다. 시스템 전역 설치는 하지 않았다. 번들 LuaJIT와 시스템 OpenSSL을 사용했다.

## 측정 정의

정상 RPS는 HTTP 200이면서 본문이 비어 있는 응답 수를 wrk 측정 시간으로 나눈 값이다.
Lua response 콜백으로 매 응답을 검증하므로 일반 무콜백 wrk 실행과 생성기 비용이 다르다.
이 콜백은 모든 조건에 동일하게 적용했다. 오류 상태·본문 불일치·소켓 오류를 별도 기록했다.
HTTP 오류율의 분모는 완료 응답 수이고, 소켓 오류 카운터는 별도다. 이를 합쳐 요청별
실패율로 해석하지 않는다. wrk의 --timeout 3s 설정도 함께 기록했다.

p95·p99는 wrk의 보정된 latency 히스토그램이며, 실제 송신 시도부터 응답 완료까지의
지연에 기반한다. TCP 연결 수립 시간은 포함하지 않으며 목표 도착률에 대한 개방형
부하 지연도 아니다. 이 시험은 기존 C10K 유지 요청 시험과 측정 목적·대상 수가 다르다.

CPU는 본 측정 wrk 프로세스 생존 구간을 기준으로 서버 /proc CPU와 생성기 자식 CPU를
읽었다. 100%는 코어 하나를 완전히 사용한 양이며 서버 값은 모든 스레드의 합이다.
워밍업 CPU·서버 시작/종료 CPU는 본 측정에서 제외한다. 서버 로그는 WSL 임시 일반
파일에 기록하고 종료 후 보관했다. 프로세스별 집계이지 메인/워커별 집계는 아니다.

## 결과 중앙값

각 행은 해당 동시성의 3회 중앙값이다. p95/p99도 실행별 백분위의 중앙값이며
15회의 요청을 합친 통합 백분위가 아니다.

| 동시성 | 정상 RPS | p95(ms) | p99(ms) | 서버 CPU | 생성기 CPU |
| --- | --- | --- | --- | --- | --- |
| 1 | 6,129 | 0.254 | 0.401 | 86.6% | 24.8% |
| 4 | 12,731 | 0.582 | 2.186 | 206.2% | 32.8% |
| 8 | 24,561 | 0.821 | 6.371 | 267.9% | 48.6% |
| 16 | 36,057 | 0.977 | 3.081 | 302.1% | 60.5% |
| 32 | 39,481 | 1.538 | 4.624 | 308.9% | 64.9% |

15회 본 측정의 HTTP 오류·본문 불일치·연결/읽기/쓰기 오류·타임아웃 카운터는 모두 0이다.
모든 서버는 정상 종료했다. 예비 1초 검사는 본 결과에 포함하지 않았다.

## 판단과 한계

- 동시성 1→4→8→16에서는 처리량이 증가했다. 16→32에서는 중앙값 36,057→39,481 RPS로 약 9.5% 증가해 증가폭이 둔화됐다.
- 같은 구간의 p95는 0.977→1.538ms, p99는 3.081→4.624ms로 증가했다. 16~32는 다음 내부 계측으로 확인할 후보 구간이다.
- 서버 CPU 중앙값은 약 302→309%, 생성기는 약 61→65%였다. 생성기 프로세스의 평균 CPU가 코어 하나에 도달한 모습은 없지만 이것만으로 생성기·스케줄링 영향이 없다고 단정하지 않는다.
- 서버 전체 CPU 합만으로 메인 직렬 처리·워커 부족·잠금·버퍼 대기 중 어느 것이 원인인지 확정할 수 없다. 다음 비교는 16·32에서 기존 내부 계측과 메인/워커별 CPU를 확인하는 것이다. 아직 수행하지 않았다.
- 최대 처리량이나 오류 한계에 도달했다고 선언하지 않는다. 동시성 64 이상과 프록시 경유는 이번 범위에서 측정하지 않았다.
- p99에는 실행 간 변동이 컸다. 동시성 1은 0.333~12.143ms, 8은 2.023~22.016ms, 16은 1.070~17.008ms였다. 느린 실행을 제외하지 않았고 원인도 확정하지 않았다.
- 총 3회와 공유 환경의 관측이다. 항상 오름차순인 실행 순서, 현재 개발 빌드, 응답 검증 콜백·로그 비용이 포함된다. 일반 환경의 성능 보장이나 프록시 성능으로 확대하지 않는다.
- 10,000개 연결 유지 실패의 원인을 이번 처리량 시험으로 확정하지 않는다. 양쪽 시험은 연결 수·요청 예약·재접속 정책이 다르다.

## 재현과 원본

공식 도구: https://github.com/wg/wrk/tree/4.2.0

```sh
# 공식 소스는 artifacts/load-tools/wrk-4.2.0에 준비한 상태
make -C artifacts/load-tools/wrk-4.2.0 -j4 WITH_OPENSSL=/usr VER=4.2.0
make webserver
# output-dir은 기존 결과를 덮어쓰지 않도록 새 경로를 사용한다.
python3 -u artifacts/load-tools/run_direct.py --seconds 30 --warmup 5 --rounds 3 --concurrency 1 4 8 16 32 --output-dir artifacts/throughput-direct-new
```

실행기는 자신의 서버와 wrk만 실행·정리하고, 자식 프로세스의 FD soft limit를 65,536으로 준비했다.
메타데이터에는 실제 OS·CPU 개수·FD 한도·서버 바이너리·wrk·Lua·실행기 SHA256이 있다.

선별 기록은 이 폴더의 metadata.json·runs.json·summary.json이다. 원본은
artifacts/throughput-direct-20261125/의 r{1,2,3}-c{1,4,8,16,32}.json,
각각의 .wrk.log·.warmup.log·.server.log이며, 생성기와 Lua는 artifacts/load-tools/에 있다.
공식 소스 압축 파일과 빌드 로그도 같은 load-tools 폴더에 보관했다.
