# 동시성 16·32의 서버 대기·CPU 계측

## 목적과 조건

직접 접속 기준 측정에서 16→32로 동시성을 높였을 때 처리량 증가가 둔화돼
배정·워커·잠금·버퍼 중 어느 구간에 대기가 쌓이는지 확인했다.

- HTTP/1.1 빈 POST /echo, 프록시 없음, wrk 4.2.0 부하 스레드 1개와 응답 검증 콜백.
- 워커 4개·작업 큐 4개·버퍼 8개·연결 상한 11,000개 고정. 프로그램의 처리·기한 정책은 유지했다.
- JUNGLE_PROFILE=1, 5초 워밍업 후 30초 본 측정. 매 실행 새 서버를 사용했다.
- 순서는 16→32 / 32→16 / 16→32다. 각 조건 총 3회.
- 기존 Makefile의 개발 빌드와 WSL Ubuntu 18.04.6 LTS, 논리 CPU 8개 환경이다.
- 기본 동시성·워커·버퍼를 조정하거나 최적화를 적용한 비교가 아니다. 새 프로파일 바이너리의 해시는 metadata.json에 있다.

## 추가한 계측

1. 버퍼 대기 최초 등록 횟수, 확보 성공까지의 wall 시간, 확보 전 취소된 대기의 wall 시간을 구분한다.
2. context_wait_started.max_units는 실제 대기열 길이의 최대값이다. 기존 풀 mutex 아래에서 길이를 읽어 추가 공용 잠금은 사용하지 않는다.
3. 버퍼 풀 mutex의 획득 wall·CPU를 별도 stage로 측정한다. 메인의 대기 선두 검사도 포함한다.
4. /proc/PID/task/TID/stat의 CPU 차이로 메인과 워커 4개의 CPU를 나눈다. 스레드 합계와 전체 프로세스 CPU의 일치를 매 실행 확인한다.

server_profile의 새 항목은 context_wait_started, context_wait_acquired_wall_only,
context_wait_cancelled_wall_only, context_mutex_wait이다. 모든 stage에 max_units를
추가했고, 대기 시작 stage에서 최대 대기자 수를 표현한다. 나머지 stage에서는 한 호출의
최대 units라는 의미이며 시간 값이 아니다. 대기 시간 stage의 max_units=0은 대기자 수를
나타내지 않으므로 반드시 context_wait_started.max_units를 사용한다.

대기 종료·취소 집계의 횟수는 실제로 대기열에서 빠진 항목 기준이다. 프로세스 종료 시
회수된 대기도 취소에 포함될 수 있다. 최초 등록 5회·성공 3회·취소 2회·최대 대기자 2명의
결정적인 풀 fixture로 계측을 검증해, 실제 부하의 0건이 누락된 구현 때문인지 구분했다.

## 측정 범위와 데이터 검증

- 스레드 CPU·생성기 CPU는 본 측정 wrk 생존 구간을 기준으로 한다. 100%는 코어 하나이며 워커 평균은 4개 워커 각각의 사용률 평균이다.
- 기존 서버 내부 stage는 시작부터 종료까지 집계해 워밍업·본 측정·정리가 함께 들어간다. 내부 stage 합계를 본 측정 30초의 CPU로 취급하지 않는다.
- 비교 표의 대기·처리는 종료 사유 없이 끝난 nonterminal 워커 차례 기준이다. HTTP 요청 1건과 항상 같은 작업 단위는 아니다.
- mutex wall은 호출의 경과 시간으로 OS 스케줄링과 잠금 구현 비용도 포함한다. 순수하게 잠금에서 재워진 시간이라고 단정하지 않는다.
- 배정 FIFO·작업 큐·워커·mutex 구간 일부는 중첩되거나 호출 수가 다르다. 최대값이나 서로 다른 항목의 평균을 더해 개별 요청 시간을 재구성하지 않는다.
- 기존 비활성 기준 측정과 활성 계측 결과는 계측 비용이 달라 성능 향상·회귀 비율로 비교하지 않는다.

초기 예비 수집에서 /proc/TID/stat을 사용했을 때 스레드마다 전체 프로세스 CPU 값이
반복되는 문제가 발견됐다. 해당 실행은 중단하고 자신의 wrk·서버만 정리한 뒤 경로를
수정했다. 그 데이터는 분석에서 제외했다. 최종 6회는 스레드별 CPU가 코어 한 개 범위에
있고 합계가 프로세스 CPU와 일치하는 검증을 통과했다.

## 이번 결과로 좁힌 부분

- 늘어난 대기는 주로 작업 큐에 들어가기 전 배정 FIFO에 쌓였다. 작업 큐 안 대기와 워커 한 차례 처리 시간은 거의 같았다.
- 동시성이 늘고 처리량이 비슷하면 추가 요청이 대기열에 머무는 것은 예상 가능한 현상이다. 이 관측만으로 FIFO 연산 구현이 느리거나 버그가 있다고 말할 수는 없다.
- 이번 빈 POST 부하에서 버퍼 확보 대기는 전혀 없었다. 처리 버퍼 8개를 늘려야 한다는 근거는 없다. 부분 I/O·큰 본문·CGI 부하에도 이 결과를 적용할 수는 없다.
- 측정 구간 평균에서 메인이나 개별 워커가 코어 하나를 포화시킨 모습은 없었다. 순간 포화나 다른 프로세스와의 CPU 경쟁까지 배제하는 자료는 아니다.
- 워커의 server mutex 획득 wall은 회당 약 26us로, context mutex의 약 1.7us보다 컸다. 동시에 배정/완료 공개가 이 공용 mutex를 사용한다. 다음 개선 실험의 후보는 이 공용 동기화·작업 전달 경로이며, 원인이 확정됐다는 뜻은 아니다.
- 단순 워커 증원이나 버퍼 확대보다 공용 mutex 아래 배정·완료 반영의 잠금 점유와 전달 비용을 확인하는 것이 우선 후보다. 아직 잠금 범위 축소·배정 묶음화·알림 병합은 적용하지 않았다.
- 내부 계측은 켠 상태로 비교했으며 RPS에 실행 간 차이가 있다. 동시성 16은 25,616~32,817 RPS, 32는 26,763~29,243 RPS였다. 일반적인 성능 한계나 C10K 유지 실패의 근본 원인을 확정하지 않는다.

## 검증과 재현

다음 검사가 통과했다. 계측을 끈 경우의 무출력과 HTTP 응답 동일성도 확인했다.

```sh
make all test_context_pool test_context test_scheduler test_server_epoll
./test_context_pool
./test_context
./test_scheduler
./test_server_epoll
python3 tests/test_server_profile.py
python3 artifacts/load-tools/run_profile.py --seconds 2 --warmup 0 --rounds 1 --concurrency 16 --output-dir artifacts/profile-smoke-new
python3 -u artifacts/load-tools/run_profile.py --seconds 30 --warmup 5 --rounds 3 --concurrency 16 32 --output-dir artifacts/profile-16-32-new
```

실행기는 output-dir이 이미 있으면 중단해 기존 결과를 덮어쓰지 않는다. 자신의 서버·
wrk만 정리한다. 초기 잘못된 경로의 결과는 INVALID.txt로 분석 제외를 표시했다.

이 폴더의 metadata.json·runs.json·summary.json·analysis.json은 선별 기록이다.
원본과 로그는 artifacts/throughput-profile-16-32-corrected-20261125/,
실행기는 artifacts/load-tools/run_profile.py다. 메타데이터의 해시로 서버 바이너리와
수집 스크립트·Lua·wrk 동일성을 확인할 수 있다. 수집 경로를 수정하기 전 데이터는
artifacts/throughput-profile-16-32-20261125/와 throughput-profile-smoke-20261125/에 있다.
