# 웹서버 완료 큐·작업 배정 FIFO

## 문제와 구현 범위

LT epoll 전환 후에도 메인은 매 루프 전체 슬롯을 읽어 완료·pending·버퍼 대기·
감시 재활성화 대상을 찾았다. 이를 변경된 연결 중심으로 처리하도록 바꿨다.
프록시, 워커4개·작업 큐4개·버퍼8개, ONESHOT, 모든 시간 제한은 유지했다.
타이머 자료구조와 context_pool의 기존 배열 기반 FIFO는 변경하지 않았다.

- 신규 연결과 워커 완료를 하나의 변경 큐에 직접 등록한다. 메인은 이 큐에서만
  완료 회수·즉시 처리·epoll 재활성화를 수행한다. 중복 등록은 합쳐진다.
- 배정 가능한 연결은 pending FIFO 뒤에 넣는다. 작업 큐에 자리가 나면 앞부터
  옮기므로 신규 작업은 기존 대기자를 추월하지 않는다. 완료 순서는 보장하지 않는다.
- 워커가 작업을 꺼내 빈자리를 만들었을 때 pending이 있으면 eventfd로 메인을
  깨운다. 작업 완료 알림도 유지한다. 큐가 사실의 원본이며 eventfd는 깨우기 수단이다.
- 버퍼 대기는 별도이다. 기존 버퍼 FIFO의 선두만 확인하고 공간이 있으면 획득·
  재개한다. 선두가 RUNNING이면 완료 알림까지 기다리고, 최초 절대2초 기한은
  유지한다. 반환·종료 후 다음 대기자도 전체 연결 검색 없이 재검사한다.
- 두 큐는 연결 내부 포인터의 이중 연결 리스트다. 각각 연결당 최대1개,
  메모리 O(연결 상한), 삽입·삭제 O(1)이며 요청별 노드 할당은 없다.
  종료 시 양쪽 큐에서 제거한 후 슬롯을 반환해 재사용된 연결의 오인 처리를 막는다.
- 큐와 상태는 기존 server mutex로 보호한다. 버퍼 FIFO 확인에는 pool mutex도
  사용한다. 워커는 pool mutex를 놓은 후 server mutex를 잡는 기존 순서를 유지한다.

이벤트 루프의 전체 슬롯 순회는 제거했지만 전체 작업을 O(1)로 만든 것은 아니다.
타이머 취소·삽입, 버퍼 소유자 검색·대기 배열 정리는 여전히 선형 비용이 있다.
종료 시 전체 슬롯 정리와 초기 슬롯 생성은 그대로다.

## 계측과 검증

prepare_scan을 prepare_changed로 바꿨다. units는 전체 슬롯 수 대신 실제 변경 큐
소비 수와 버퍼 대기 선두 확인 수의 합이다. 처리 대상 종류가 다르므로 같은 단위의
속도 비율로 해석하지 않는다. 구간에는 타이머·작업 배정·감시 갱신 비용도 포함된다.
SP_NOTIFY는 기존 완료 알림을 계측하며, 작업 큐 빈자리 알림은 별도 집계하지 않는다.

- test_server_epoll: 신규/완료 큐 중복 방지, 무변경 루프의 재등록 없음,
  pending 포화·중복·FIFO·신규 추월 방지·중간/선두 삭제·슬롯 재사용 검사 통과.
- 버퍼 FIFO의 슬롯 순서와 다른 선두 재개, 공간 부족 시 대기 유지,
  절대 기한 유지·만료 후 회수 검사 통과.
- 스케줄러·컨텍스트·계측 검사, 기존 TCP 통합11개·CGI8개 검사 통과.
- 1000개 유지·재사용·회수 통과. 10000건 첫 요청 성공, 동시 연결 유지 미통과.

```sh
make all test_scheduler test_context test_server_epoll
./test_scheduler && ./test_context && ./test_server_epoll
python3 tests/test_server_profile.py
python3 proxy/tests/test_proxy.py
python3 src/tests/test_cgi.py
python3 tests/check_capacity.py --connections 1000 --empty-body --rounds 1 --server-profile --proxy-profile --output artifacts/server-queues/server-queues-1000.json
python3 tests/check_capacity.py --connections 10000 --empty-body --rounds 1 --server-profile --proxy-profile --output artifacts/server-queues/server-queues-10000.json
```

## 단회 측정 결과

기존 server-epoll-10000.json과 같은 설정이다. 연결 상한11000·버퍼8·동시 요청4·
빈 POST·1회 순회·양쪽 계측 활성 조건이며 부하 실행기는 변경하지 않았다.

| 10000건 | 변경 전 | 변경 후 |
| --- | --- | --- |
| 요청 wall | 8.201초 | 9.456초 |
| 요청 구간 웹서버 CPU | 7.50초 | 6.71초 |
| 요청 구간 프록시 CPU | 2.09초 | 2.65초 |
| 요청 구간 생성기 CPU | 8.502초 | 10.499초 |
| 메인 준비 누적 CPU | 2.601초 | 1.058초 |
| 준비 확인 수 | 슬롯178,761,000개 | 변경/선두27,360건 |
| 첫 검사 앞단 / 백엔드 | 5911 / 4734개 | 5085 / 3997개 |

준비 경로와 웹서버 CPU는 줄었지만 전체 처리 시간과 유지 연결 수는 개선되지
않았다. 공유 WSL의 별도 단회 실행이며 생성기·프록시 CPU도 달라 전체 성능 향상
또는 회귀의 원인을 이 결과만으로 단정하지 않는다. 내부 누적 CPU와 요청 구간
프로세스 CPU는 범위가 다르고 중첩 구간을 합산하지 않는다.

1000개 요청 wall은0.788초·웹서버 CPU0.25초이다. 실패 처리 도중의 추가 연결
스냅샷은 첫 검사와 시점이 달라 원본 JSON의 observed_established와 차이가 날 수 있다.
원본은 server-queues-1000.json, server-queues-10000.json이다.

다음 후보는 그대로 남은 정렬 타이머의 선형 갱신·취소 비용이다. 기존 연결을
유지하면서 새 연결을 늘리는 부하 생성기 개선도 별도 과제다. 시험 방식 변경의
효과를 서버 자체의 최적화 효과와 분리하고 C10K 유지를 다시 검증해야 한다.
