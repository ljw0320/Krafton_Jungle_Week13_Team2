# 웹서버 완료 큐·배정 FIFO 반복 비교

## 방법

- 이전: `9dd357f`, 현재: `80b5a16`. 각3회, 순서 이전→현재 / 현재→이전 / 이전→현재이다.
- 각 커밋을 별도 임시 디렉터리에 추출하고 같은 컴파일러·Makefile 옵션으로 빌드했다. 현재 체크아웃과 실행 파일은 바꾸지 않았다.
- 프록시는 현재 커밋에서 한 번 빌드한 동일 바이너리를 양쪽에 복사했다. 부하 실행기 파일의 해시 일치도 확인했다.
- 빈 POST10000건·동시 요청4·버퍼8·연결 상한11000·양쪽 계측 활성·1회 순회이다. 매회 프로세스를 새로 시작하고 종료 후 다음 실행을 시작했다.
- 별도 워밍업·캐시 초기화는 없다. 성공한 비교 실행의 빌드·집계 포함 시간은 125.48초이다.

## 해석

- 웹서버 CPU와 준비 경로 CPU는 현재 버전3회 모두 이전 버전3회의 범위보다 낮았다. 전체 검색 축소의 CPU 절감은 이번 반복에서도 확인됐다.
- 요청 wall 중앙값은15.092→11.103초이다. 다만 범위가 겹치고 세 번째 짝에서는 현재가11.396→12.592초로 느렸다. 매번 더 빠르다는 결과는 아니다.
- 이전4번 실행은27.113초이지만 웹서버 CPU11.38초로 이전1번의11.47초와 비슷하다. CPU 밖 대기·실행 스케줄링 등의 영향이 의심되나 별도 계측 없이 원인을 확정하지 않는다. 이 실행도 제외하지 않고 집계했다.
- 기존 단회8.20→9.46초만으로 구조 변경이 느려졌다고 판단할 근거는 부족하다. 이번에는 CPU 절감과 wall 중앙값 감소가 관측됐지만 버전당3회·공유 WSL 조건이므로 일반적인 개선율이나 통계적 유의성을 주장하지 않는다.
- 6회 모두 첫 요청10000건은 성공했고 동시 연결 유지 검사는 실패했다. 프로세스 종료 코드1은 유지 수 assertion 실패이며, 비교 스크립트는 이를 원본에 그대로 남기고 정상 집계했다.
- 첫 검사 연결 수와 실패 처리 중 추가 관측값은 시점이 다르다. 내부 준비 CPU는 시작·종료 정리를 포함하며 요청 구간 프로세스 CPU와 범위가 달라 합산하지 않는다.

## 재현·원본

- `tests/compare_server_versions.py`: 비교 스크립트. 기존 runs.json이 있으면 덮어쓰지 않고 중단하므로 재실행 기본 경로는 artifacts 아래의 새 타임스탬프 폴더이며, --output-dir로 별도 경로를 지정할 수 있다.
- `metadata.json`: 전체 커밋, 빌드 환경, 서버·프록시·실행기 해시, 조건과 순서.
- `01-before.json`~`06-after.json`: 각 실행의 원본 계측.
- `runs.json`, `summary.json`: 개별 결과와 중앙값·최소·최대 집계.
- 일반 프로그램·원래 부하 실행기 코드는 변경하지 않았다.
