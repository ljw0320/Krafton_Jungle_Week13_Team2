# 웹서버 인덱스 최소 힙 타이머

## 적용 범위와 이유

완료 큐 적용 후에도 타이머 취소·삽입은 정렬 단일 연결 리스트에서 위치를 찾는
O(N) 작업이었다. 연결이 자신의 힙 위치를 기억하는 인덱스 최소 힙으로 바꿨다.
다음 기한 조회 O(1), 등록·갱신·취소 O(log N)이며 연결당 타이머는 최대1개다.

- 연결 상한만큼 포인터 배열을 시작 시 할당하고 종료 시 해제한다. 요청 처리 중
  타이머용 추가 할당은 없다. 배열의 활성 구간만 사용하고 빈 끝 항목은 NULL이다.
- 연결의 timer_position은 1부터 시작하며0은 미등록이다. 연결 memset과 슬롯 재사용
  이후에도 기본값이 미등록이다. 힙 이동 때 위치를 갱신하고 삭제 때0으로 무효화한다.
- 마감 변경은 기존 항목을 제자리 갱신하고 위·아래 필요한 방향으로만 재정렬한다.
  반복 등록으로 항목이 늘거나 오래된 항목이 쌓이지 않는다. 미등록 취소는 무해하다.
- 기존 server mutex로 보호한다. WAITING에서 등록, 배정·종료 때 취소하는 소유권은
  유지한다. 같은 마감 시각의 처리 순서는 보장하지 않으며 별도 버퍼·작업 FIFO는 유지한다.
- 수신5초·송신3초·keep-alive5초/100회·버퍼 최초 고갈2초·정리 절대 기한·CGI2초와
  종료 재확인 시각의 계산은 변경하지 않았다. 프록시·완료 큐·배정 FIFO·부하 생성기도 그대로다.

## 비교 방법과 계측 해석

직전 f815a7c의 정렬 리스트와 현재 작업 트리의 힙을 각각 별도 임시 디렉터리에서
같은 옵션으로 빌드한다. 실행 순서는 이전→현재 / 현재→이전 / 이전→현재다.
미커밋 코드는 HEAD 위 소스 복사본·파일별 SHA256·변경 패치로 기록하고, 현재
체크아웃과 실행 파일을 이전 버전으로 바꾸지 않는다. 프록시는 한 번 빌드한 동일
실행 파일이고 부하 실행기 파일의 동일성도 확인한다.

빈 POST10000건·동시 요청4·연결 상한11000·버퍼8·양쪽 계측 활성·1회 순회 조건이다.
기본 결과는 Git 제외 artifacts에 저장하고 이번 대표 수치와 원본은 이 폴더에 보관한다.
공유 WSL의 버전당3회 결과이며 별도 워밍업·캐시 초기화는 없다.

타이머 units는 리스트 링크 이동 횟수에서 힙 기한 비교 횟수로 바뀌었다. 같은
종류의 연산 속도로 해석하지 않는다. 기존 timer_update에는 내부 timer_cancel이
포함됐지만 힙에서는 제자리 갱신하므로 정상 갱신에 취소가 포함되지 않는다.
update와 cancel을 더하면 기존 값의 중복 계산이 발생한다. 내부 누적 CPU와
요청 구간 프로세스 CPU도 측정 범위가 달라 합산하지 않는다.

6회 모두 첫 요청10000건은 성공했고 동시 연결 유지는 미통과다. 첫 검사 시
이전 앞단/백엔드는2678/2018, 3176/2489, 5045/4139개, 현재는4283/3493,
4135/3406, 5582/4345개다. 실패 처리 중 재관측 값은 시점이 달라 구분해야 한다.
전체102.34초는 이번 비교의 빌드·실행·집계 시간이며 기능 검사 시간은 제외한다.

한 순회 중 먼저 열린 연결을 갱신하지 않는 생성기와 유휴4~5초 정책은 그대로다.
타이머 개선 후에도 생성기·프록시·스케줄링 비용과 연결 유지 방식이 전체 시간에
영향을 줄 수 있다. 원인을 분리하지 않은 상태에서 새 병목을 확정하지 않는다.
다음 후보는 메인 알림 횟수 계측·병합과 별도 C10K 유지 부하 개선이다.

원본은 같은 폴더의01-before.json~06-after.json, runs.json, summary.json,
metadata.json, after-source.patch이다. 작업 버전의 소스 SHA256·변경 패치와 기준
커밋을 남겼다. 프로파일 구간의 중첩과 반복3회의 한계 때문에 일반적인 개선율을
보장하지 않는다.
