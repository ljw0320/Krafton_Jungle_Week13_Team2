# 비동기 C10K 연결 유지 검증

## 목적과 구현 범위

기존 check_capacity.py는 전체 연결을 한 바퀴 처리한 뒤에야 다음 순회를 시작해
먼저 열린 연결이 유휴4~5초를 넘을 수 있었다. 이 실행기는 이전 성능 비교의
재현성을 위해 변경하지 않았다. 새 tests/check_c10k.py는 연결을 늘리는 중에도
기존 연결에 유지 요청을 보내는 별도 검증 도구다. 서버·프록시 코드는 변경하지 않았다.
기준 프로그램은 힙 타이머 적용 커밋 f221b2b이다.

- asyncio 비차단 TCP, 기본 동시 요청4개. --concurrency는 버퍼 상한 이하에서 지정한다.
- 완료 시각+2초를 다음 유지 요청 시각으로 최소 힙에 저장한다. 기한이 된 기존
  연결을 신규 연결보다 먼저 처리한다. 연결당 동시에 한 요청만 발행한다.
- 기본 부하는 과거와 같은 빈 POST /echo다. --nonempty-body는 식별 본문 echo를
  검증하는 다른 부하다. 서로 다른 본문·동시성·계측 조건을 성능 개선율로 비교하지 않는다.
- 응답 상태200·Content-Length·Connection·Via·본문을 확인한다. 자동 재접속은 없다.
  EOF·리셋·응답 오류·요청3초 제한·유지 응답 간격3.5초 초과는 실패다.
- 전체 연결 도달 후 최소6초 동안 유지하며 최소2회씩 응답받아야 한다. 6초는
  백엔드4초·클라이언트5초 유휴보다 길다. 전체 검사 상한은 기본60초다.
- 유지 중 별도 Python 프로세스가 proxy PID의 /proc FD와 TCP 표를 읽어 앞단·
  백엔드 ESTABLISHED 수를 여러 번 확인한다. Python GIL·파싱이 생성기를 직접
  막지 않도록 분리했다. 이것이 모든 측정 간섭을 제거한다는 뜻은 아니다.
- 프런트 TCP 생성 수와 백엔드 accept 수가 목표와 같아야 하며, 종료 후 양쪽
  연결0개 회수를 검사한다. 준비 확인용 백엔드 접속1개는 accept 집계에서 제외한다.
- 유지 간격 위반은 보수적인 검사 실패이며 실제 서버 유휴 종료를 항상 뜻하지는 않는다.
  initialized는 첫 응답 성공 누적 수이며, 그만큼 동시 유지가 검증됐다는 뜻도 아니다.

## 필요한 검사

작은 실제 TCP fixture2개로 신규 연결 추가 중 기존 연결 재사용, 동시 요청 상한,
끊어진 연결의 재접속 금지를 검증했다. 서버 기능 변경이 없어 기존 HTTP·CGI
전체 회귀 검사를 다시 실행하지 않고, 실제 서버의 유지·회수 검사에 집중했다.

```sh
make all
python3 tests/test_c10k_loader.py
python3 tests/check_c10k.py --connections 1000
python3 tests/check_c10k.py --connections 10000
# 별도 부하 조건: 서버 설정은 그대로, 생성기 동시 요청만8개
python3 tests/check_c10k.py --connections 10000 --concurrency 8
```

기본 결과는 artifacts/c10k-retain-<연결수>-<시각>.json이다. --output으로 경로를,
--profile로 양쪽 내부 계측 활성 여부를 지정한다. 새 결과에는 실행 바이너리
SHA256도 기록한다. 대표 결과 JSON은 이 폴더에 선별 보관했다.

## 결과

| 조건 | 결과 | 관측 |

| 1000개·동시4·빈 POST·계측 꺼짐 | 통과 | 도달0.655초, 도달 후6.331초 유지, 모든 연결4회 응답, 총4000요청 |
| 10000개·동시4·빈 POST·계측 꺼짐 | 미통과 | 첫 응답9365개 누적, 응답 간격3.500051초에서 검사 실패 |
| 10000개·동시8·빈 POST·계측 꺼짐 | 미통과 | 첫 응답8440개 누적 뒤 연결 리셋, backend keep_alive_timeout3259건 |
| 10000개·동시4·빈 POST·계측 켜짐 | 미통과 | 첫 응답10000개 누적·도달38.706초, 이후 간격3.500568초에서 실패. 전체 유지 스냅샷 성공은 없음 |

1000개는 네 번의 스냅샷에서 앞단1000·백엔드1000개를 확인했다. 최대 유지 응답
간격2.042초, 프런트 TCP 생성1000개·백엔드 accept1000개로 재연결 없이 재사용했고,
종료 후 양쪽0개 회수도 확인했다. 위 도달·유지 시간은 처리량 벤치마크가 아니다.

초기에는 식별 본문을 쓰는 별도 부하도 시험했으나 유지 간격을 넘겼다. 본문이 있는
요청의 결과를 빈 POST와 섞지 않았다. 패킷·ACK 지연 등 구체 원인은 계측하지 않아
확정하지 않는다. 최초 빈 POST10000개 시험도 지연으로 실패했다. 표에는 스냅샷
분리 구현 후의 계측 꺼짐4/8개 조건과 진단용 계측 켜짐 결과를 보관했다.
계측 켜짐 진단 결과는 이전 스레드 기반 스냅샷 구현에서 얻은 값으로 구분한다.

## 해석과 다음 과제

유지 요청을 보내도록 시험을 바꿨지만 C10K 통과를 얻지는 못했다. 동시 요청을
8개로 늘려도 실패했으므로, 생성기 동시성만 늘리면 해결된다는 결론은 아니다.
반대로 이번 실패만으로 서버가 다른 환경·부하에서도10000개를 유지할 수 없다고
단정하지 않는다. 공유 WSL의 단회 결과이며 서버·프록시·생성기·스케줄링 영향을
분리한 실험은 아니다.

다음은 지속적인 유지 요청 부하에서 요청 지연·생성기 처리량·각 프로세스 CPU를
같은 시간 구간으로 계측하는 것이다. 필요한 갱신률과 실제 처리율, deadline 지연을
분리하고 메인 깨우기·작업 배정 비용을 확인해야 한다. 서버 시간 제한을 늘리거나
자동 재접속으로 통과시키는 방식은 적용하지 않았다. 기존 순회형 결과와 이 결과의
차이를 서버 자체 최적화 효과로 기록해서는 안 된다.


## 요청 시각 최소 계측 추가

결과 observation.request_timing에 첫 요청(first)과 유지 요청(reuse)을 나누어
예약→코루틴 시작, 예약→송신 호출, 송신 호출→drain 완료, 송신 호출→응답 완료의
count·total·maximum과 최대값 요청의 원본 시각(max_request)을 기록한다.
평균은 total/count로 계산한다. 요청별 로그를 출력하거나 전체 이력을 쌓지 않는다.

시각은 같은 프로세스의 time.monotonic 초 값이다. scheduled_at은 유지 요청에서는
직전 응답 완료+heartbeat, 첫 요청에서는 신규 연결 배정 시각이다. 첫 요청의
예약→송신에는 TCP 연결 수립이 포함되며 전체 ramp의 지연을 뜻하지 않는다.
send_at은 StreamWriter.write 직전, drained_at은 drain 반환 직후이고,
response_completed_at은 응답 본문 수신·검증 완료 시각이다. 송신 호출이나 drain은
실제 패킷 출발·서버 수신 시각을 보장하지 않는다. 송신→응답에는 네트워크와
생성기 이벤트 루프의 재개 지연도 포함되어 서버 처리 시간으로 단정할 수 없다.

실패 시 timing_at_stop에는 관측 시각, 응답 미완료 요청, 가장 오래된 유휴 연결의
다음 예약 시각과 직전 요청 시각을 남긴다. 미완료 단계의 시각은 null이다.
진행 중 요청은 정리 취소 전에 캡처하며 완료 지연 통계에는 포함하지 않는다.
기존 예약 방식·동시성·시간 제한·통과 기준은 유지했다.

추가 후 기존 TCP fixture 2개와 실제 서버 32개 연결 유지·재사용·회수 검사가
통과했다. 32개 결과는 artifacts/c10k-timing-smoke.json이며 C10K 재시험은 아니다.
