# 비동기 C10K 연결 유지 검증

## 목적과 구현 범위

기존 check_capacity.py는 전체 연결을 한 바퀴 처리한 뒤에야 다음 순회를 시작해
먼저 열린 연결이 유휴4~5초를 넘을 수 있었다. 이 실행기는 이전 성능 비교의
재현성을 위해 변경하지 않았다. 새 tests/check_c10k.py는 연결을 늘리는 중에도
기존 연결에 유지 요청을 보내는 별도 검증 도구다. 서버·프록시 코드는 변경하지 않았다.
기준 프로그램은 힙 타이머 적용 커밋 f221b2b이다.

- asyncio 비차단 TCP, 기본 동시 요청4개. --concurrency는 버퍼 상한 이하에서 지정한다.
- 완료 시각+2초를 다음 유지 요청 시각으로 최소 힙에 저장한다. 기한이 된 기존
  연결을 신규 연결보다 먼저 처리한다. 연결당 동시에 한 요청만 발행한다.
- 기본 부하는 과거와 같은 빈 POST /echo다. --nonempty-body는 식별 본문 echo를
  검증하는 다른 부하다. 서로 다른 본문·동시성·계측 조건을 성능 개선율로 비교하지 않는다.
- 응답 상태200·Content-Length·Connection·Via·본문을 확인한다. 자동 재접속은 없다.
  EOF·리셋·응답 오류·요청3초 제한·유지 응답 간격3.5초 초과는 실패다.
- 전체 연결 도달 후 최소6초 동안 유지하며 최소2회씩 응답받아야 한다. 6초는
  백엔드4초·클라이언트5초 유휴보다 길다. 전체 검사 상한은 기본60초다.
- 유지 중 별도 Python 프로세스가 proxy PID의 /proc FD와 TCP 표를 읽어 앞단·
  백엔드 ESTABLISHED 수를 여러 번 확인한다. Python GIL·파싱이 생성기를 직접
  막지 않도록 분리했다. 이것이 모든 측정 간섭을 제거한다는 뜻은 아니다.
- 프런트 TCP 생성 수와 백엔드 accept 수가 목표와 같아야 하며, 종료 후 양쪽
  연결0개 회수를 검사한다. 준비 확인용 백엔드 접속1개는 accept 집계에서 제외한다.
- 유지 간격 위반은 보수적인 검사 실패이며 실제 서버 유휴 종료를 항상 뜻하지는 않는다.
  initialized는 첫 응답 성공 누적 수이며, 그만큼 동시 유지가 검증됐다는 뜻도 아니다.

## 필요한 검사

작은 실제 TCP fixture2개로 신규 연결 추가 중 기존 연결 재사용, 동시 요청 상한,
끊어진 연결의 재접속 금지를 검증했다. 서버 기능 변경이 없어 기존 HTTP·CGI
전체 회귀 검사를 다시 실행하지 않고, 실제 서버의 유지·회수 검사에 집중했다.

```sh
make all
python3 tests/test_c10k_loader.py
python3 tests/check_c10k.py --connections 1000
python3 tests/check_c10k.py --connections 10000
# 별도 부하 조건: 서버 설정은 그대로, 생성기 동시 요청만8개
python3 tests/check_c10k.py --connections 10000 --concurrency 8
```

기본 결과는 artifacts/c10k-retain-<연결수>-<시각>.json이다. --output으로 경로를,
--profile로 양쪽 내부 계측 활성 여부를 지정한다. 새 결과에는 실행 바이너리
SHA256도 기록한다. 대표 결과 JSON은 이 폴더에 선별 보관했다.

## 해석과 다음 과제

유지 요청을 보내도록 시험을 바꿨지만 C10K 통과를 얻지는 못했다. 동시 요청을
8개로 늘려도 실패했으므로, 생성기 동시성만 늘리면 해결된다는 결론은 아니다.
반대로 이번 실패만으로 서버가 다른 환경·부하에서도10000개를 유지할 수 없다고
단정하지 않는다. 공유 WSL의 단회 결과이며 서버·프록시·생성기·스케줄링 영향을
분리한 실험은 아니다.

다음은 지속적인 유지 요청 부하에서 요청 지연·생성기 처리량·각 프로세스 CPU를
같은 시간 구간으로 계측하는 것이다. 필요한 갱신률과 실제 처리율, deadline 지연을
분리하고 메인 깨우기·작업 배정 비용을 확인해야 한다. 서버 시간 제한을 늘리거나
자동 재접속으로 통과시키는 방식은 적용하지 않았다. 기존 순회형 결과와 이 결과의
차이를 서버 자체 최적화 효과로 기록해서는 안 된다.


## 요청 시각 최소 계측 추가

결과 observation.request_timing에 첫 요청(first)과 유지 요청(reuse)을 나누어
예약→코루틴 시작, 예약→송신 호출, 송신 호출→drain 완료, 송신 호출→응답 완료의
count·total·maximum과 최대값 요청의 원본 시각(max_request)을 기록한다.
평균은 total/count로 계산한다. 요청별 로그를 출력하거나 전체 이력을 쌓지 않는다.

시각은 같은 프로세스의 time.monotonic 초 값이다. scheduled_at은 유지 요청에서는
직전 응답 완료+heartbeat, 첫 요청에서는 신규 연결 배정 시각이다. 첫 요청의
예약→송신에는 TCP 연결 수립이 포함되며 전체 ramp의 지연을 뜻하지 않는다.
send_at은 StreamWriter.write 직전, drained_at은 drain 반환 직후이고,
response_completed_at은 응답 본문 수신·검증 완료 시각이다. 송신 호출이나 drain은
실제 패킷 출발·서버 수신 시각을 보장하지 않는다. 송신→응답에는 네트워크와
생성기 이벤트 루프의 재개 지연도 포함되어 서버 처리 시간으로 단정할 수 없다.

실패 시 timing_at_stop에는 관측 시각, 응답 미완료 요청, 가장 오래된 유휴 연결의
다음 예약 시각과 직전 요청 시각을 남긴다. 미완료 단계의 시각은 null이다.
진행 중 요청은 정리 취소 전에 캡처하며 완료 지연 통계에는 포함하지 않는다.
기존 예약 방식·동시성·시간 제한·통과 기준은 유지했다.

추가 후 기존 TCP fixture 2개와 실제 서버 32개 연결 유지·재사용·회수 검사가
통과했다. 32개 결과는 artifacts/c10k-timing-smoke.json이며 C10K 재시험은 아니다.


## 전송 전 대기 원인 분리 계측

요청 예정→송신 시간을 다음 세 구간으로 나눈다. 동시 요청 상한과 예약·배정 방식은
변경하지 않았다. 서버·프록시 코드는 변경하지 않았다.

- slot_full_wait_seconds: 예정→배정 구간 중, 배정된 미완료 요청이 동시성 상한과 같았던 시간.
- slot_available_wait_seconds: 같은 구간 중 미완료 요청 수가 상한 미만이었던 시간.
- admission_to_send_seconds: 배정→송신 호출 시간. 첫 요청은 TCP 연결 수립도 포함한다.

세 구간의 합은 schedule_to_send_seconds다. first/reuse별 count·total·maximum 및
최대 요청 원본을 기존 request_timing 형식으로 집계한다. 개별 요청의 최대값 샘플에도
세 구간을 같이 보관하므로 같은 요청 안에서 지연을 분해할 수 있다.

미완료 요청은 태스크 배정부터 exchange의 finally 진입까지로 정의한다. 응답이 끝났지만
예약 루프가 아직 완료 태스크를 회수하지 못한 시간은 실제 요청이 미완료인 시간과
구분해 빈자리 시간으로 계산한다. 연결 수립·로컬 버퍼 대기·네트워크·응답 대기와
코루틴 재개 지연 모두 미완료 구간에 포함되어 full 시간만으로 서버 병목을 뜻하지 않는다.
빈자리 시간도 이 연결보다 먼저 예약된 다른 연결의 처리, 태스크 완료 전달·회수,
이벤트 루프·OS 스케줄링·계측 비용이 섞이므로 특정 테스트기 버그로 단정하지 않는다.

상한 도달·해제 시각과 누적 full 시간을 두 개의 숫자 배열에 저장하고 이진 검색한다.
모든 대기 연결을 매번 순회하지 않으며 요청별 파일 로그는 추가하지 않았다. 히스토리는
시험 중 유지되며 전이 수에 비례해 메모리와 검색 비용이 증가한다. capacity_timing에는
시험 경과 시간·전체 full 시간·전이 수·배열 데이터 바이트 수를 남긴다.
history_bytes는 배열 데이터 크기이며 Python 객체와 할당 여유 공간을 포함한 전체
메모리 사용량은 아니다. 종료·실패 시 미송신 요청은 완료 지연 분해 통계에 포함되지 않는다.

### 단회 확인 결과

동일한 빈 POST·10,000개·동시 요청 4개·버퍼 각각 8개·서버/프록시 프로파일 활성 조건이다.
28.231초에 통과했고 유지 요청 100,057개의 송신 전 지연을 분해했다.

| 유지 요청 구간 | 평균 | 최대 |
| --- | --- | --- |
| 예정→송신 전체 | 114.365ms | 698.197ms |
| 배정 전 상한 포화 시간 | 57.938ms | 375.698ms |
| 배정 전 빈자리 시간 | 56.276ms | 346.193ms |
| 배정→송신 | 0.151529ms | 56.287ms |
| 송신→응답 | 0.529979ms | 32.644ms |

각 행의 최대값은 서로 다른 요청이므로 합산하지 않는다. 전체 송신 전 지연이 최대인
동일 요청에서는 698.197ms = 포화 372.741ms + 빈자리 325.302ms + 배정 후 0.154ms였다.
두 종류의 배정 전 대기가 비슷하게 섞였으며 동시성 상한만이 원인이라는 근거는 없다.
단회 결과로 예약 루프 개선이나 동시성 확대의 효과를 확정하지 않는다.
계측 비용이 추가되므로 이전 실행과 처리 시간 개선율로 비교하지 않는다.

정확한 포화 구간 적분·중복 반환, 실제 TCP에서 구간 합계·건수 일치·재사용·동시성 상한,
오류 시 슬롯 반환과 재접속 금지 검사 총 3개가 통과했다.
원본은 artifacts/c10k-capacity-split-10000.json에 저장했다.

```sh
python3 tests/test_c10k_loader.py
python3 tests/check_c10k.py --connections 10000 --profile --output artifacts/c10k-capacity-split-10000.json
```


## 동시 요청 4개·8개 비교 — 각각 3회

서버·프록시 설정을 고정하고 테스트기의 concurrency만 4와 8로 바꿨다.
순서는 4→8→4→8→4→8이며 매번 새 서버·프록시 프로세스로 실행했다.
동일 바이너리 SHA256, 목표 10,000개, 연결 상한 각각 11,000개, 버퍼 각각 8개,
빈 POST, 유지 요청 주기 2초, 서버·프록시 프로파일과 생성기 대기 분리 계측 활성이다.
유지 응답 간격 3.5초 미만·목표 도달 후 최소 6초 유지·전체 제한 60초 등의 판정은 같다.
이번 작업에서 실행 코드를 추가 변경하지 않았다.

| 서버 배정 FIFO 대기 평균의 중앙값 | 0.002876ms | 0.008885ms |
| 서버 작업 큐 대기 평균의 중앙값 | 0.076360ms | 0.105425ms |
| 서버 워커 처리 평균의 중앙값 | 0.065004ms | 0.067309ms |

세 쌍 모두 동시 8개에서 목표 도달 시간이 짧았고 포화 대기 평균도 줄었다.
따라서 동시 요청 4개 제한이 이 실행기의 연결 증가 속도에 영향을 줬다는 근거다.
8개에서 서버 큐 대기와 송신 후 응답 평균은 증가했으나 이번 시험에서는 짧은 수준을
유지했고 워커 처리 평균도 비슷했다. 워커나 서버 작업 큐를 확대해야 한다는 근거는
이번 비교에서도 확보하지 못했다.

두 조건 모두 3/3 통과했으므로 8개가 유지 안정성을 개선했다거나 과거 실패 원인이
4개 제한이었다고 확정할 수 없다. 동시 8개는 부하 조건 변경이며 서버 코드 개선이 아니다.
목표 도달이 빨라지면 증가 중 기존 연결을 갱신하는 횟수도 달라진다. 실제 총 요청 수는
4개 조건 87,536~121,335건, 8개 조건 62,769~74,194건으로 같지 않으므로 전체 시간 비율을
서버 처리량 개선율로 해석하지 않는다. 항상 4개 다음에 8개를 실행한 순서 효과와 공유
WSL 변동, 계측 비용도 남아 있다. 3회씩의 기술적 관측이며 일반적인 성능 보장은 아니다.

구간별 중앙값·최대값은 동일 요청의 지연이 아니므로 합산하지 않는다. 빈자리 대기에는
다른 연결의 우선 배정, 태스크 완료 전달·회수, 이벤트 루프와 OS 스케줄링 등이 포함된다.
아직 이 내부 원인을 분리하거나 생성기의 기본 동시성을 변경하지 않았다.

전체 집계·조건·바이너리 해시·실행별 지연은 concurrency-compare-summary.json에 보관했다.
원본 6개는 artifacts/c10k-concurrency-compare-c{4,8}-r{1,2,3}.json이다.

python3 tests/check_c10k.py --connections 10000 --concurrency 4 --profile --output artifacts/c10k-concurrency-compare-c4-r1.json
