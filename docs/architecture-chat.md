# 설계: 무작위 1:1 채팅

범위: 직접 만든 웹 서버 위에서 무작위 1:1 채팅을 만든다. 서버에는 WebSocket 터널과 상태 JSON을 더하고, 채팅은 리버스 프록시 뒤의 C 프로그램 `chatd`가 맡는다. 이 문서와 다른 설계 문서가 다르면 채팅 단계에서는 이 문서를 따른다.

요구사항: [requirements.md](requirements.md)의 "채팅 서비스". 프록시: [architecture-proxy.md](architecture-proxy.md)

이 문서에서 **A**는 브라우저와 서버의 연결, **B**는 서버와 `chatd`의 연결이다. `위`는 A → B, `아래`는 B → A 방향이다.

---
# 의도

- 사용자가 로컬에서 직접 써 볼 수 있으면 끝이다. 글을 쓰면 테스트 상대가 답한다.
- 수천 명이 글을 주고받고 한순간에 몰려도 서버와 `chatd`가 죽지 않는다.
- 클라이언트 → 내 서버 → 백엔드로 흐르는 실제 요청을 페이지로 본다.

하지 않는 것: 로그인, 닉네임, 대화 기록 저장, 이미지 저장, 방 3인 이상, 신고/차단, TLS, 공개 배포, 프록시가 아닌 곳의 8KB 본문 한도 변경, 압축(`permessage-deflate`)

실패로 보는 것: 프로세스가 죽는다, 메모리가 끝없이 는다, 상대가 연결되어 있는데 글이 사라지거나 순서가 바뀐다, 흐름 페이지가 지어낸 숫자를 보여 준다.

---
# 검토한 방식

| 방식 | 장점 | 단점 |
|---|---|---|
| 1. **WebSocket 터널 + C 백엔드 (선택)** | 글마다 연결하지 않는다. 이미지도 같은 연결로 보내 8KB 본문 한도를 고치지 않는다. 느린 상대가 TCP를 통해 보내는 쪽을 늦춘다 | 양방향 중계, SHA-1, Base64, 프레임 파서를 직접 만든다 |
| 2. SSE + POST | 지금 프록시로 받기가 거의 된다 | 글 1건마다 B를 새로 연결한다. 이미지 때문에 본문 처리를 바꾼다. 퇴장을 늦게 안다 |
| 3. WebSocket 터널 + Python 백엔드 | 코드가 가장 적다 | 과제의 "언어: C"에 걸릴 수 있다 |

선택 이유: 부하에서 죽지 않는 것이 핵심 목표다. 2번은 글마다 연결을 맺어 이 목표와 어긋난다. 1번은 C 제약을 지킨다. 2026-11-25 사용자가 1번을 골랐다.

# 서버: WebSocket 터널

## 요청 판정 (`http.c`)

`http_parse`가 아래를 모두 만족하면 `req->ws = 1`로 둔다. 하나라도 아니면 0이고 지금 동작 그대로다.
- `GET`, `HTTP/1.1`, 본문 없음(`content_length == 0`)
- `Connection` 토큰에 `upgrade`, `Upgrade` 토큰에 `websocket`(대소문자 무시)

`Sec-WebSocket-Key`와 `Version`은 `chatd`가 검사한다.

```c
/* 헤더 값 하나를 찾는다. 1: 하나 있음, 0: 없음, -1: 두 개 이상 */
int http_header(const struct http_req *req, const char *buf, const char *name, const char **v, size_t *n);
/* GET이면 200 JSON, 아니면 405. 실패하면 -1 */
int http_json(const struct http_req *req, const char *body, size_t len, struct http_resp *resp);
/* ws 인자를 더한다. ws가 1일 때만 101을 허용한다 */
ssize_t http_proxy_response(const char *buf, size_t len, int minor, int keep, int ws,
                            char *out, size_t cap, struct http_upresp *r);
```

- `http_proxy_request`: `req->ws`면 `Connection: close` 대신 `Connection: Upgrade`와 `Upgrade: websocket`을 쓴다. 나머지 규칙은 같다.
- `http_proxy_response`: `ws`이고 `101`이면 다음을 검사하고 어기면 502다. 응답이 `HTTP/1.1`, `Upgrade` 토큰에 `websocket`, `Connection` 토큰에 `upgrade`, `Content-Length`와 `Transfer-Encoding` 없음. 통과하면 `Connection: Upgrade`, `Upgrade: websocket`을 새로 만들고 나머지 헤더를 옮긴다.
- `ws`인데 `101`이 아닌 응답(400, 404, 503)은 일반 응답으로 중계한다.
- `up_head`의 `1xx` 버리기 반복은 `ws`인 `101`에서 멈춘다.

## 상태와 필드

- `enum conn_state`에 `CONN_TUNNEL`, `enum up_state`에 `UP_TUNNEL`을 더한다.
- `struct conn`에 `size_t roff`(B로 보낸 rbuf 위치), `uint32_t trace`를 더한다. `struct upstream`에 `int ws`를 더한다.
- 버퍼를 새로 만들지 않는다. 위 방향은 `rbuf`(8192), 아래 방향은 `wbuf`(16384)를 쓴다.

```c
int tunnel_start(struct conn *c);                         /* wbuf에 101과 뒤따른 바이트가 있다 */
int tunnel_on_client(struct conn *c, uint32_t events);    /* 모두 0 또는 -1(닫음) */
int tunnel_on_backend(struct conn *c, uint32_t events);
void tunnel_sweep(struct conn *c, time_t now);
```

- `tunnel_start`: 두 상태를 바꾸고 A의 `SO_SNDBUF`를 정하고, rbuf에 남은 바이트는 위 방향의 첫 데이터로 쓴다. B의 소켓 버퍼는 `req->ws`일 때 `connect` 전에 정한다.
- `conn_on_readable`, `conn_on_writable`, `proxy_event`는 터널 상태면 위 함수로 보낸다. `event_loop.c`는 바꾸지 않는다.

## 중계 규칙

| | 위 (A → B) | 아래 (B → A) |
|---|---|---|
| 읽는 조건 | `rlen == 0` | `woff == wlen` |
| 한 이벤트 | `recv` 한 번, 이어서 `send` 한 번 | 같다 |
| 다 보냄 | `rlen = roff = 0` | `wlen = woff = 0` |

- 다 보내기 전에는 읽지 않는다. 연결 하나의 사용자 메모리가 약 25KB로 고정된다.
- 감시: A는 `(rlen == 0 ? IN : 0) | (woff < wlen ? OUT : 0)`, 0이면 `EPOLLERR`. B는 `(woff == wlen ? IN : 0) | (roff < rlen ? OUT : 0)`, 0이면 `loop_unwatch`(프록시의 backpressure와 같은 이유). 값이 달라질 때만 `loop_watch`를 부른다.
- 이벤트 종류가 아니라 `recv`, `send`의 반환값으로 판단한다. B의 `ERR|HUP`은 IN을 감시 중이면 읽기, 아니면 쓰기로 처리한다.
- `recv`가 0이나 오류, `send`가 오류면 `conn_close`. 읽는 조건 때문에 그때 그 방향에 보낼 것이 남아 있지 않다. 반대 방향의 남은 바이트는 버린다.

## 타이머 (`tunnel_sweep`, 1초마다)

| 조건 | 처리 |
|---|---|
| 양방향 모두 바이트가 30초 넘게 움직이지 않음 (`last_active`) | 닫는다. `chatd`가 10초마다 ping을 보내므로 정상 연결은 걸리지 않는다 |
| 아래로 보낼 것이 남았고 A가 10초 넘게 받지 않음 (`up.since`) | 닫는다. `SIOCOUTQ`가 줄면 받는 중이다(기존 sweep과 같은 방법). `up.since`는 `recv(B)` 성공(아래로 보낼 것이 생김), `send(A)` 성공, `SIOCOUTQ` 감소 때 적는다. 마지막 전송 때만 적으면 오래 조용하던 방의 첫 전송이 `EAGAIN`일 때 바로 닫는다 |

기존 10초 유휴, 요청 타이머, `proxy_timeout`은 터널에 쓰지 않는다.

## `/_stat`

`conn_process`가 `route_find`보다 먼저 대상이 정확히 `/_stat`인지 보고 `stat_json` → `http_json`으로 답한다.

```json
{"now_us":0,"conns":0,"tunnels":0,"up":{"n":0,"bytes":0},"down":{"n":0,"bytes":0},
 "pending":0,"rss_kb":0,"events":[{"seq":1,"trace":123,"stage":"A>S","bytes":20,"t_us":0}]}
```
- `n`은 `recv`에 성공한 횟수(중계 횟수), `bytes`는 보낸 바이트, `pending`은 열린 터널의 아직 못 보낸 바이트 합이다. 서버는 글의 수를 모른다.
- `rss_kb`는 `/proc/self/statm`에서 읽는다.
- `events`는 최근 64개다. `stage`는 `A>S`(A에서 받음), `S>B`(B로 보냄), `B>S`, `S>A`. `trace`가 0인 연결은 남기지 않는다.
- `trace`는 쿼리의 `trace=<1~4294967295>`다. 형식이 틀리면 0이다. `?` 뒤를 `&`로 나눠 처음 나온 `trace=`만 본다. 서버와 `chatd`가 같은 함수를 쓴다.

# 백엔드: `chatd`

## 상수

| 이름 | 값 | 뜻 |
|---|---|---|
| `MAX_USERS` | 6000 | WebSocket 사용자 |
| `MAX_CONNS` | 6064 | 핸드셰이크 중과 상태 조회까지 포함한 연결. 넘으면 accept하자마자 닫는다 |
| `FRAME_MAX` | 16384 | 프레임 하나의 payload |
| `TEXT_MAX` | 4096 | 합친 텍스트 메시지 하나(첫 글자 포함) |
| `IN_CAP` | `FRAME_MAX + 14` | 받는 버퍼 |
| `OUT_CAP` | 65536 | 보낼 큐 |
| `OUT_RESERVE` | 1024 | 제어용으로 남기는 큐 |
| `IMG_MAX` | 2097152 | 이미지 1장 |
| `MATCH_MS` | 500 | 매칭 주기 |
| `PING_SEC` / `DEAD_SEC` | 10 / 30 | ping 주기 / 받은 바이트가 없으면 닫음 |
| `HANDSHAKE_SEC` / `SLOW_SEC` | 10 / 10 | 핸드셰이크 제한 / 큐가 줄지 않으면 닫음 |

연결 하나의 최대는 약 87KB, 6,064개면 약 515MB다. 큐가 비면 앞으로 되돌려 쓰므로 평소에는 앞쪽 페이지만 쓴다.

## HTTP

`src/http.c`의 `http_parse`로 요청 하나를 읽는다. 한도는 8192바이트다.

| 요청 | 응답 |
|---|---|
| `GET /ws/chat[?...]`, `req.ws`, `Sec-WebSocket-Version: 13`, 키가 Base64 16바이트 | `101` + `Sec-WebSocket-Accept` |
| 같은 경로, `req.ws`가 아님 또는 키 오류 | 400 |
| 버전이 13이 아님 | 426 + `Sec-WebSocket-Version: 13` |
| `GET /ws/stat` | 200 JSON |
| GET이 아님 / 그 밖의 경로 / 형식 오류 | 405 / 404 / 파서의 코드 |
| 사용자가 `MAX_USERS`명일 때의 업그레이드 | 503. 요청을 다 읽은 뒤 보내야 RST로 사라지지 않는다. 남는 64자리는 이 거절과 `/ws/stat`이 쓴다 |

검사 순서는 405(`Allow: GET`) → 404 → 400 → 426 → 503이다. 사용자 수는 `101`을 큐에 넣을 때 센다.

101이 아닌 응답은 `Content-Length`와 `Connection: close`를 붙이고 닫는다. 키 확인값: `dGhlIHNhbXBsZSBub25jZQ==` → `s3pPLMBiTxaQ9kYGzzhZRbK+xOo=`.

## 프레임 검사

어기면 close 프레임(코드)을 큐에 넣고 다 보낸 뒤 닫는다.

| 위반 | 코드 |
|---|---|
| 마스크 없음, RSV 비트, 모르는 opcode, 최소가 아닌 길이 표현, 제어 프레임이 125바이트 초과 또는 FIN 0, 이어지는 프레임의 순서 오류 | 1002 |
| payload가 `FRAME_MAX` 초과, 합친 텍스트가 `TEXT_MAX` 초과 | 1009 |
| 텍스트의 UTF-8 오류 (그대로 넘기면 상대 브라우저가 연결을 끊는다) | 1007 |
| 빈 텍스트, 모르는 메시지 종류, 글 없는 `m`, `n` 뒤의 글자, 이미지 규칙 위반 | 1008 |

- 나뉜 텍스트는 합친 뒤 처리한다. Chrome은 빠르게 보낼 때 프레임을 나눌 수 있다. 나뉜 바이너리는 합치지 않고 조각마다 전달한다.
- ping은 pong으로 답하고, pong은 무시한다. close는 같은 코드로 답하고 닫는다. payload가 비었으면 빈 close로 답하고, 1바이트면 1002다. 코드 값과 이유는 검사하지 않는다.

## 메시지

| 방향 | 프레임 | 뜻 |
|---|---|---|
| 클라 → | `m<글>` | 글. 1바이트 이상 |
| 클라 → | `i<jpg 또는 png> <바이트 수>` | 이미지 시작. 이어서 그 크기만큼 바이너리 |
| 클라 → | 바이너리 | 이미지 조각 |
| 클라 → | `n` | 다음 상대. 지금 상대를 떠나고 대기열로 간다 |
| → 클라 | `w` / `c` / `l` | 대기 중 / 상대와 연결됨 / 상대가 나감 |
| → 클라 | `m<글>`, `i...`, 바이너리 | 상대가 보낸 것 |
| → 클라 | `a` | 내 글 `m` 하나가 상대의 큐에 들어감. 순서대로 온다 |
| → 클라 | `s<접속> <대기>` | 대기 중인 사람에게 1초마다 |

이미지: 크기는 숫자 1~7자리이고 값은 1~`IMG_MAX`, 종류는 `jpg`, `png`만. 이미지를 보내는 중에 `i`를 또 보내거나, `i` 없이 바이너리를 보내거나, 선언보다 많이 보내면 1008이다. 이미지 중간에 `m`은 보낼 수 있다. 빈 바이너리는 무시한다.

## 사용자 상태

```
HANDSHAKE ─101─▶ WAITING ─매칭─▶ PAIRED ─상대가 떠남─▶ ALONE
                   ▲                │ n                  │ n
                   └────────────────┴────────────────────┘
어느 상태든 ─ 위반, close ─▶ CLOSING ─ 큐를 다 보냄 ─▶ 닫음
```
- 한쪽이 떠나면(`n`, 끊김, 위반) 상대는 `l`을 받고 `ALONE`이 된다. 양쪽의 이미지 진행 상태를 지운다.
- `WAITING`, `ALONE`에서 온 `m`, `i`, 바이너리는 조용히 버린다. 상대가 막 떠난 순간에 날아온 것이며 다음 상대에게 가면 안 된다. 같은 연결의 순서가 보장되므로 `n` 앞의 데이터는 이전 상대의 것이다. `ALONE`의 남은 이미지 조각도 버려야 하므로 `n`을 받을 때까지 이미지 규칙을 검사하지 않는다. 내용을 보지 않고 버리므로 글 없는 `m`도 버린다. 빈 텍스트, 모르는 종류, `n` 뒤의 글자는 이때도 1008이다.
- `WAITING`에서 온 `n`은 무시한다.

## 매칭

`room.c`의 `shuffle(int *a, int n)`은 Fisher-Yates, 난수는 시작할 때 시드를 정한 `random()`이다. 0.5초마다 대기자가 2명 이상이면 섞고 둘씩 잇는다. 홀수면 한 명이 남는다. 같은 상대를 다시 만날 수 있다.

## 보내기와 backpressure

- 상대 큐의 빈 자리가 `프레임 전체 길이 + OUT_RESERVE`보다 작으면 그 프레임을 처리하지 않고 보낸 사람의 읽기를 멈춘다(`EPOLLIN` 끔). 보낸 사람의 ping/pong도 밀린다.
- `m`은 자기 큐의 빈 자리도 `3 + OUT_RESERVE`(`a` 하나) 이상일 때만 처리하고, 아니면 자기 읽기를 멈춘다. 상대의 글로 자기 큐가 차 있을 때 중간 버퍼에 쌓인 자기 글이 처리되면 `a`가 예약 자리를 넘어 정상 사용자가 끊기기 때문이다. 자기 큐는 자기가 읽으면 비므로 서로 기다리지 않는다.
- 자기 앞으로 가는 제어(`a`, `c`, `l`, `w`, pong, close)가 큐에 안 들어가면 그 사람을 닫는다. `s`와 ping은 이번에 보내지 않는다.
- 큐에 넣을 때 `send`하지 않고 **더티 목록**에 올린다. 이벤트 배치가 끝나면 한 번씩 `send`한다. `EAGAIN`이면 `EPOLLOUT`을 켠다. 글마다 `epoll_ctl`을 부르지 않고 여러 글이 한 번에 나간다.
- 큐가 절반 아래로 비면 그 큐를 기다리던 사람(상대와 본인)의 남은 프레임을 이어서 처리한다. 더티 목록이 빌 때까지 반복하되 이 단계에서는 `recv`하지 않으므로 반드시 끝난다.
- 멈춘 사람이 `CLOSING`이 되거나 짝이 바뀌면 멈춤을 푼다.
- `free`는 배치가 끝난 뒤 한다. 같은 배치에 남은 이벤트는 `dead` 표시를 보고 건너뛴다. 닫을 때 상대의 포인터, 대기열, 더티 목록에서 먼저 뺀다.
- 느린 사람: 큐가 비지 않았고 10초 동안 `send` 성공이나 `SIOCOUTQ` 감소가 없으면 닫는다. 멈춰 있는 사람은 30초 무응답 검사에서 뺀다.

## `/ws/stat`

```json
{"now_us":0,"users":0,"waiting":0,"rooms":0,"msgs":0,"img_bytes":0,"paused":0,"queued":0,
 "slow_closed":0,"rejected":0,"rss_kb":0,
 "events":[{"seq":1,"trace":123,"stage":"recv","kind":"m","bytes":20,"t_us":0}]}
```
`stage`는 `recv`(프레임을 해석함), `send`(추적 중인 사람의 큐에 넣음), `kind`는 메시지 첫 글자이며 바이너리는 `b`다. 최근 64개다.

# 화면

시작 주소는 `/chat.html`과 `/flow.html`이다. `/`의 화면은 만들지 않는다.

## `chat.html`
- 상태: 대기(접속/대기 수, 취소), 대화(다음 상대, 나가기), 상대가 나감(다음 상대), 끊김(다시 연결). 시안은 2026-11-25에 보여 줬고 고칠 점은 없었다. 취소와 나가기는 연결을 닫고 시작 화면으로 간다.
- `ws://<지금 주소>/ws/chat?trace=<무작위 정수>`로 연결한다. 글은 `textContent`로만 넣는다. 입력은 1,000자까지, 빈 글은 보내지 않는다. Enter로 보내고 한글 조합 중(`isComposing`)에는 보내지 않는다.
- 이미지: 고른 파일의 앞 바이트가 JPG(`FF D8 FF`)나 PNG(`89 50 4E 47`)이고 2MB 이하인지 확인한다. 16KB로 나누고 `bufferedAmount`가 256KB를 넘으면 기다린다. 보내는 동안 이미지 버튼을 끈다. `l`, `n`이면 멈춘다.
- 받는 쪽은 선언한 크기를 다 받으면 `Blob`(`image/jpeg` 또는 `image/png`)으로 `<img>`를 보여 준다. 짝이 바뀌면 주소를 해제한다.
- 글을 보낼 때 시각을 줄에 넣고 `a`가 오면 꺼내 왕복 시간을 잰다. `l`, `n`이면 줄을 비운다. `BroadcastChannel('flow')`로 `{trace, n, rtt_ms}`를 보낸다.
- 버튼과 입력에 이름을 붙이고 메시지 목록은 `aria-live="polite"`다. 휴대폰 폭에서도 가로로 넘치지 않는다.

## `flow.html`
- 위는 세 칸(클라이언트, 내 서버, 백엔드)과 두 길(요청, 응답), 아래는 숫자와 내 글 목록, 오른쪽(좁으면 아래)은 `chat.html` iframe이다. 한 화면에서 글을 치고 흐름을 본다.
- `/_stat`과 `/ws/stat`을 0.2초마다 읽는다. 앞 요청이 끝나지 않았으면 건너뛴다. 실패하면 그 칸을 빨갛게 하고 "응답 없음"을 적는다.
- 회색 점: 늘어난 중계 횟수에 비례해 초당 최대 60개. 점 하나가 나타내는 횟수를 화면에 적는다.
- 파란 점: `trace`가 같은 이벤트를 시각 순으로 이어 `A>S` → `S>B` → `recv`, `send` → `B>S` → `S>A`로 움직인다. 느리게 그렸다는 것을 화면에 적는다.
- 내 글 목록: `kind`가 `m`인 `recv`마다 그 앞의 가장 늦은 `S>B`와의 차이, `kind`가 `a`인 `send`와 그 뒤 첫 `B>S`의 차이, 왕복을 적는다. 짝이 없으면 `-`다.
- 폴링이 만드는 `/_stat`, `/ws/stat` 요청은 중계 횟수에 들어가지 않는다(터널만 센다).

# 봇과 부하 시험: `tests/chat_bot.py`

Python 표준 라이브러리만 쓴다. `python3 tests/chat_bot.py <모드> [옵션]`, 기본 주소는 `127.0.0.1:8080`이다.

| 모드 | 동작 | 통과 (종료 코드 0) |
|---|---|---|
| `echo` | 글마다 0.3초 뒤 정해진 문장 중 하나를 답한다. 이미지에는 "사진 잘 봤다"고 답한다. `l`이면 `n` | 끝나지 않는다 |
| `load --users 5000 --rate 1 --sec 60` | 초당 1,000명씩 접속, 모두 짝지어진 뒤 보낸다 | 아래 공통 |
| `burst --users 5000 --n 20 --rounds 3` | 모두가 동시에 20건씩 보낸다 | 아래 공통 |
| `flood --users 200 --sec 30` | 쉬지 않고 보낸다(미확인 글의 수를 제한하지 않는다). 봇마다 5초에 한 번 1초 동안 읽지 않는다 | 아래 공통, 시험 중 `paused`가 1 이상인 때가 있다 |
| `slow --users 200` | 모두 계속 보낸다. 절반은 `c`를 받은 뒤 읽지 않는다(`SO_RCVBUF` 4096. 크면 커널이 대신 받아 준다). `--witness`는 먼저 접속해 짝지은 뒤 나머지가 접속한다 | 안 읽는 쪽이 10~30초에 끊김(서버와 `chatd` 중 누가 끊어도 된다). 나머지 대화(`--witness 100`)는 유실 0 |
| `image --users 200` | 100명이 동시에 2MB를 보낸다 | 받은 바이트의 sha256이 같다. 첫 전송부터 마지막 수신까지 5초 안 |
| `churn --users 1000 --sec 30` | 접속하고 글을 보내다 RST로 끊기를 반복. 회차마다 `a`를 기다리지 않고 전송 중에 끊는다 | 끝난 뒤 `users`가 원래 수로 돌아옴. 아래의 유실과 끊김 기준은 쓰지 않고 순서만 본다 |

공통 통과 기준
- 보낸 글(`a`를 받은 수) = 받은 글. 보낸 사람별 번호가 1씩 는다.
- `load`는 첫 전송부터 마지막 `a`와 글을 받을 때까지 `--sec` + 5초 안이고 `a` 지연의 최대가 2초 이하다.
- 예상하지 않은 끊김 0건. 두 프로세스가 살아 있다.
- 시험 중 `/_stat`, `/ws/stat`이 1초마다 2초 안에 답한다.
- RSS: 서버 300MB 이하, `chatd` 600MB 이하.

여러 프로세스(`--procs`, 기본 4)로 나눠 접속하고 부모가 합계를 낸다. 짝은 다른 프로세스에 있을 수 있으므로 순서는 받는 쪽이, 합계는 부모가 확인한다. 봇이 병목이면 초당 건수를 실제 값으로 출력하고, 목표에 못 미치면 실패로 끝낸다. 시험 중에는 사람이 새로 접속하지 않는다. 사람과 `echo` 봇은 먼저 짝지어 둔다.

5,000명 시험은 `make test`에 넣지 않고 `make load`로 따로 돌린다. 표의 값으로 `load`, `burst`, `flood`, `slow`, `image`, `churn`을 차례로 돌린 뒤, `chatd`에 직접 6,000명을 접속해 6,001번째가 503인지 본다(8080을 거치면 fd가 두 배 든다). 하나라도 실패하면 멈춘다. `make test`에는 200명 이하의 짧은 판을 넣는다.

# 엣지 케이스

| 상황 | 기대 |
|---|---|
| WebSocket 요청이 아닌데 백엔드가 `101` | 502 (지금과 같다) |
| `Upgrade: h2c`, `HTTP/1.0`, `POST`, 본문 있는 업그레이드 | `ws`가 아니다. `Upgrade`를 빼고 보내고 `chatd`는 400 또는 405 |
| `101`과 첫 프레임이 한 `recv`에 옴 | 첫 프레임도 A로 간다 |
| `101` 전에 A가 프레임을 먼저 보냄 | 터널이 열린 뒤 B로 간다 |
| `chatd`가 꺼짐 | 새 연결은 502, 열린 연결은 닫힘. 화면은 "다시 연결" |
| 서버를 거친 프레임이 1바이트씩 옴 | 정상 처리 |
| 한 `recv`에 프레임 여러 개 | 순서대로 처리 |
| 길이 125 / 126 / 65535 / 16384 / 16385 | 경계마다 정상 또는 1009 |
| 큐가 가득 찬 상대 | 보낸 사람만 멈추고 다른 방은 그대로 |
| 서로 큐가 가득 찬 두 사람(둘 다 보내기만) | 10초 뒤 먼저 막힌 쪽이 끊기고 남은 쪽은 `l`. 같은 때 막혔으면 둘 다 끊긴다 |
| 이미지 도중 상대가 나감 | 나머지 조각을 버리고 다음 상대에게 가지 않음 |
| 2MB + 1바이트, 0바이트, `gif`, 음수, 숫자 아닌 크기 | 1008 |
| 6,001번째 사용자 | 503, 앞의 사람들과 `/ws/stat`은 그대로 |
| fd 부족 | `chatd`의 accept가 멈췄다가 fd가 비면 다시 받는다 |
| 같은 배치에서 두 짝이 함께 끊김 | ASan 오류 없음 |
| 대기 중에 끊긴 사람 | 매칭되지 않음 |
| 잘못된 UTF-8, 서로게이트, 과장된 표현(overlong) | 1007, 상대는 `l`만 받음 |

# 알려진 한계

- 속도 제한은 없고 사용자 수만 제한한다. 한 사람이 계속 보내면 상대의 속도까지만 막힌다.
- `Origin`을 검사하지 않는다. 로그인이 없어 다른 사이트가 연결해도 익명 사용자와 같다. 공개하려면 검사를 더한다.
- `/_stat`, `/ws/stat`은 누구나 볼 수 있다. 공개하려면 막는다.
- 이미지의 내용은 검사하지 않는다. 받는 쪽 `<img>`가 해석한다.
- 닫을 때 A에서 아직 안 읽은 바이트가 있으면 RST가 나가 마지막 close 프레임이 사라질 수 있다(기존 lingering close 한계).
- 5,000명이 모두 동시에 멈추면 커널 소켓 메모리(`tcp_mem` 722MB)가 먼저 부족해질 수 있다. 이때 새 연결이 실패할 수 있다.
- 봇, 서버, `chatd`가 같은 PC에서 돈다.
- 느린 사람의 판정은 커널 송신 큐의 변화다. 받는 쪽의 TCP 창은 버퍼의 절반쯤 비어야 다시 열리므로, 읽고 있어도 10초에 그만큼 못 읽으면 끊긴다(초당 4KB로 읽는 사람이 끊긴 예가 있다).
- 양쪽 모두 읽지 않아 각 송신 큐가 10초 동안 정체되면 먼저 막힌 연결을 닫고 상대에게 `l`을 보낸다. 같은 점검에서 두 연결 모두 기한을 넘기면 양쪽을 닫을 수 있다.
- 로그를 동기로 쓴다. 로그 파일이 느린 곳(`/mnt/c`)에 있으면 수천 명이 한꺼번에 나갈 때 이벤트 루프가 몇 초 멈춘다. `run_chat.sh`는 `/tmp`에 쓴다.

## 구현하는 사람이 정하는 것

함수 안의 나누기, 내부 구조체 이름, 로그 문구, 화면의 색과 간격, 봇의 답장 문장. 메시지 형식, 상수, 상태 코드, JSON 키는 이 문서를 따른다.
