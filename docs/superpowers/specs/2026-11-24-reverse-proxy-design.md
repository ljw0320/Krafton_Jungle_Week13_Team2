# 경로 기반 리버스 프록시 설계

작성일: 2026-11-24 (Asia/Seoul)

상태: 사용자가 구현을 승인한 확정 설계. 구현 세부사항을 아래에 반영했으며 검증 결과는 구현 계획 문서에 기록한다.

## 목적과 범위

C/POSIX 소켓으로 작성한 기존 fork 기반 HTTP 서버에 경로 기반 리버스 프록시를 추가한다. 지정한 경로의 GET·POST 요청을 설정된 백엔드에 전달하고 응답을 중계한다. 나머지 요청은 기존 정적 파일·CGI 처리로 연결한다.

외부 HTTP·이벤트 루프 라이브러리는 사용하지 않는다. 기존 HTTP/1.1 클라이언트 연결 유지, 프로세스 상한, 종료·회수 구조를 활용한다. 프록시와 웹 서버는 하나의 실행 파일에서 공존하며, 백엔드는 별도 HTTP 서버다.

이번 범위에는 포워드 프록시, 로드밸런싱, HTTPS/TLS, 캐싱, 자동 재시도, 백엔드 연결 풀, DNS 조회, 설정 실시간 재적용을 포함하지 않는다. 응답 경계 지원은 Content-Length와 본문 없는 응답에 한정한다. chunked·연결 종료 기반 응답으로 확장할 것을 전제로 구조를 만들지 않는다.

## 검토한 접근과 선택 이유

| 접근 | 장점 | 비용·제약 | 결정 |
| --- | --- | --- | --- |
| 호스트 기반 라우팅 | 서비스별 도메인 분리, 백엔드가 루트부터 경로 사용 | 로컬 도메인 설정, Host 라우팅 검증 필요 | 선택하지 않음 |
| 경로 기반 라우팅 | 기존 경로별 정적·CGI 분기 활용, 하나의 주소로 확인 가능 | 접두사 경계·우선순위·전달 경로 정책 필요 | 선택 |
| 모든 요청을 백엔드로 전달 | 백엔드 하나면 단순, 중계 역할 집중 | 기존 정적·CGI 배치 변경, 여러 서비스 라우팅을 별도로 정해야 함 | 기본 배치로 선택하지 않음 |

모든 요청 전달은 라우팅 기준과 별개의 배치 선택이다. `/` 규칙으로 일반 요청 전체를 중계할 수 있지만 CGI 예약 영역은 직접 처리한다.

본문 전달은 전체 버퍼링과 스트리밍을 비교했다. 전체 버퍼링은 수신 완료 후 오류 응답을 결정할 수 있지만 저장 공간과 첫 전송 지연이 발생한다. 헤더 전체 검증 후 본문 스트리밍을 선택해 메모리를 제한한다. 전송 시작 후 백엔드 실패 시 불완전한 응답과 연결 종료가 발생할 수 있다는 비용을 수용한다.

## 라우팅과 URL 정책

- 경로로 라우팅하며 쿼리는 매칭에 사용하지 않는다.
- 경로 요소 경계로 매칭한다. `/api`는 `/api`, `/api/users`와 일치하지만 `/apix`, `/api-v2`와는 일치하지 않는다.
- 여러 규칙과 일치하면 가장 긴 접두사를 선택한다. `/api/admin`은 `/api`보다 우선한다.
- `/` 규칙은 모든 일반 경로와 일치한다.
- 백엔드에 전달할 요청의 경로와 쿼리는 유지한다. `/api/users?page=1`은 동일한 요청 대상으로 전달한다. 접두사를 제거하지 않는다.
- 규칙에 일치하지 않으면 기존 정적 파일·CGI 처리로 연결한다.
- `/cgi-bin` 영역은 예약한다. 기존 CGI 분기를 프록시보다 우선하며, 다른 CGI 경로의 기존 404 정책도 유지한다.
- `/cgi-bin` 및 그 하위 경로를 프록시 규칙으로 지정하면 설정 오류로 거부한다. `/` 규칙도 이 예약을 우회하지 않는다.
- 프록시로 선택한 요청은 백엔드 실패 시 정적 파일·CGI로 재시도하지 않는다.

실제 `/api`, `/assets` 배치는 설명용 예시다. 운영 경로·포트는 설정으로 지정하며 하드코딩하지 않는다.

## 설정

기존 실행 인자에 `--routes routes.conf`를 추가하는 형태로 라우팅 파일을 지정한다. 생략하면 기존 서버로 실행한다.

```sh
./build/web-server 8080 public 64 5 5 --routes routes.conf
```

```text
# 경로 접두사  백엔드 IPv4  포트
/api          127.0.0.1    8001
/assets       127.0.0.1    8002
```

- 한 줄은 경로 접두사·숫자 IPv4·포트의 세 필드다.
- 빈 줄과 `#`으로 시작하는 주석 줄을 허용한다.
- 경로는 `/`로 시작한다. `/` 자체를 제외하면 끝의 `/`는 금지한다. 쿼리·프래그먼트는 금지한다.
- 중복 경로는 거부하며 서로 다른 중첩 경로는 허용한다.
- 백엔드 주소는 숫자 IPv4만 허용한다. 포트는 1~65535다.
- 부모가 시작 시 한 번 읽고 검증하며 자식은 상속한 설정을 읽기만 한다.
- 파일 읽기·검증 실패는 줄 번호와 원인을 출력하고 시작 실패로 처리한다. 파일 열기 실패처럼 줄 번호가 없는 오류는 파일 경로와 원인을 표시한다.
- 변경 적용은 재시작으로 한다.

## 프로세스·연결 수명

기존 연결 담당 자식이 클라이언트 소켓과 백엔드 소켓을 관리한다. 프록시용 프로세스를 추가 생성하지 않는다.

```text
요청 헤더 수신·검증 → 경로 선택 → 백엔드 socket/connect
    → 요청 전달 → 응답 헤더 수신·검증 → 본문 스트리밍
    → 백엔드 연결 종료 → 기존 정책에 따라 클라이언트 연결 유지·종료
```

- 요청마다 백엔드 TCP 연결을 새로 만들고 응답 처리가 끝나면 닫는다.
- 클라이언트 연결 유지와 백엔드 연결 재사용은 독립적이다. 클라이언트는 기존 keep-alive 정책을 따른다.
- 클라이언트가 끊기면 백엔드 작업도 중단하고 연결을 닫는다. 이미 백엔드에서 실행된 부작용의 취소를 보장하지 않는다.
- 중계 실패 시 관련 fd·버퍼를 정리한다. 불완전한 응답 뒤에 다음 응답을 보내지 않는다.
- 자동 재시도는 하지 않는다. POST 등의 중복 실행을 피한다.

## 요청 전달·헤더 정책

- 기존 지원 메서드인 GET·POST를 중계한다. 요청 본문을 버리지 않고 정확한 길이만큼 전달한다.
- 원래 Host는 유효성을 검사한 뒤 유지한다. TCP 목적지는 Host가 아닌 설정된 백엔드다.
- 연결 전용 헤더와 Connection 필드가 지목한 헤더는 제거한다. 요청·응답 양방향에 적용한다.
- 백엔드 요청에는 프록시가 `Connection: close`를 설정한다.
- 의미를 가진 일반 헤더는 전달한다. 반복 가능한 헤더는 각각 보존하며 Set-Cookie 등을 무조건 합치지 않는다.
- 클라이언트의 `Forwarded`·`X-Forwarded-*`는 제거하고 새로 생성하지 않는다. 원래 클라이언트 IP는 백엔드에 전달하지 않는다.
- `Expect: 100-continue`는 프록시가 기존 방식으로 처리하고 Expect를 백엔드에 전달하지 않는다.
- 메시지 길이 헤더는 검증한 실제 처리 방식과 일치하도록 구성한다. 연결 헤더 제거 때문에 메시지 경계 검증을 우회해서는 안 된다.

## 백엔드 응답 검증과 경계

상태 줄·헤더 전체를 수신해 검증한 뒤에만 클라이언트에 응답을 시작한다. HTTP/1.0·1.1을 허용한다.

| 조건 | 처리 |
| --- | --- |
| 상태 줄·헤더 문법 오류 | 502 |
| Content-Length 중복 | 동일 값이어도 502 |
| 길이 형식 오류·숫자 오버플로 | 502 |
| Transfer-Encoding 존재 | 502, 지원하지 않음 |
| 본문이 가능한 최종 응답에서 Content-Length 누락 | 502, 연결 종료 방식으로 추측하지 않음 |
| Content-Length: 0 | 헤더에서 완료 |
| 204 | 본문 없음, Content-Length가 있으면 거부 |
| 304 | 본문 없음, Content-Length가 있어도 본문을 읽지 않음 |
| 1xx (101 포함) | 미지원, 502 |
| 유효한 백엔드 4xx·5xx | 프록시 실패로 바꾸지 않고 전달 |

일반 최종 응답은 선언된 Content-Length만큼 정확히 수신·전달해야 한다. 조기 EOF는 불완전한 응답이다. 본문 없는 응답도 헤더 문법·중복 등 검증에서 면제되지 않는다.

## 크기·본문 중계

| 대상 | 정책 |
| --- | --- |
| 클라이언트 URI | 기존 8KiB 유지 |
| 클라이언트 헤더 | 기존 32KiB 유지 |
| 클라이언트 본문 | 기존 1MiB 유지 |
| 백엔드 응답 헤더 | 상태 줄·종료 빈 줄 포함 32KiB. 초과 시 502 |
| 응답 본문 버퍼 | 16KiB |
| 응답 본문 총량 | 별도 정책 상한 없음. 표현 범위 오버플로 거부 |

백엔드 본문은 전체를 모으지 않고 고정 크기 버퍼로 중계한다. 메모리 사용량이 본문 총량에 비례하지 않도록 한다. 클라이언트가 느리면 백엔드 읽기도 늦춰 무제한 버퍼 누적을 막는다.

## 시간 제한

| 구간 | 확정 정책 |
| --- | --- |
| 백엔드 TCP 연결 | 전체 5초 |
| 백엔드로 요청 전송 | 전송 진전 없는 상태 10초 |
| 백엔드 응답 헤더 수신 | 요청 전송 완료부터 전체 10초 |
| 백엔드 응답 본문 수신 | 수신을 기다리는 동안 진전 없는 상태 10초 |
| 클라이언트로 응답 전송 | 전송 진전 없는 상태 10초, 기존 정책 활용 |

진전은 실제 바이트 송수신이다. 준비 이벤트만으로 기한을 연장하지 않는다. 클라이언트 전송 대기로 백엔드 읽기를 멈춘 시간은 백엔드 무응답으로 계산하지 않는다.

응답 본문 전체 기한은 두지 않는다. 계속 진행되는 느린 전송이 자식을 오래 점유할 수 있다는 제약을 수용한다. 기존 클라이언트 요청 수신 기한은 유지한다.

## 오류·로그

| 실패 | 응답 전송 전 |
| --- | --- |
| 백엔드 연결 거절·리셋, 잘못된·미지원 응답 | 502 |
| 백엔드 연결·요청 전송·응답 대기 기한 초과 | 504 |
| 메모리 할당 등 프록시 자체 내부 실패 | 500 |
| 클라이언트 끊김·전송 무진전 | 연결 정리, 백엔드 오류 응답으로 바꾸지 않음 |

클라이언트로 응답을 일부라도 보내기 시작한 후 실패하면 새 오류 응답을 덧붙이지 않는다. 양쪽 연결을 닫고 기록한다. 전송 전 오류의 클라이언트 연결 유지 여부는 아래 구현 세부사항에서 명시한다.

실패 로그에는 원인과 가능한 경우 예상 본문 길이·수신 바이트·전달 바이트를 남긴다. 아직 길이를 알 수 없는 실패는 미확인으로 구분한다. 로그는 정상 결과 복구를 대신하지 않는다.

## 이번 구현에서 구체화한 세부사항

다음은 확정 정책을 구현하기 위해 내가 정한 세부사항이다. 별도의 추가 사용자 결정이 필요한 항목으로 남겨두지 않는다.

- 설정은 최대 128개 규칙, 개행 포함 줄당 16KiB다. 공백·탭으로 필드를 구분하고 앞 공백 뒤 # 주석을 허용하되 인라인 주석은 허용하지 않는다. NUL은 거부한다.
- 설정 경로는 ASCII 영숫자·`/-._~`로 제한하고 중복 슬래시·점 요소·퍼센트 인코딩을 허용하지 않는다. 요청은 기존 decode_path로 한 번 디코딩한 경로를 매칭에만 사용한다. CGI 예약 분기가 먼저 실행되며 전달 target은 디코딩하거나 재작성하지 않는다. 프록시 경로에 정적 파일의 숨김 파일·openat 정책을 적용하지 않는다.
- 프록시 Host는 ASCII DNS 형식 이름 또는 대괄호 IPv6와 선택 포트(1~65535)를 검증한다. HTTP/1.0에서도 Host가 없으면 400이다. 외부 호스트 허용 목록은 추가하지 않는다.
- 제거할 연결 전용 헤더는 Connection·Proxy-Connection·Keep-Alive·TE·Trailer·Upgrade·Proxy-Authenticate·Proxy-Authorization이며 Connection 지목 필드도 제거한다. Connection이 Host·Content-Length·Transfer-Encoding을 지목하면 요청 400, 응답 502다.
- 프록시 요청 본문은 기존 1MiB 제한·30초 수신 기한 안에서 메모리에 먼저 보관한다. 요청 전송 중 백엔드가 먼저 응답하면 전송을 중단하고 응답 처리로 전환하며 클라이언트 연결은 닫는다.
- 백엔드 요청은 HTTP/1.1로 구성하고 클라이언트 응답 버전·연결 헤더는 기존 클라이언트 정책에 맞춘다.
- 응답 길이는 uintmax_t의 부호 없는 십진수로 검증하고 오버플로·쉼표 목록을 거부한다. 최종 상태 코드는 200~599, 헤더는 CRLF와 토큰 이름을 요구하고 줄 접기·NUL·금지 제어 문자를 거부한다.
- 응답 전송 전 프록시 오류에서도 클라이언트 연결을 닫는다. 요청 본문 잔여분과 다음 요청을 혼동하지 않도록 한다.
- 로그는 stderr 한 줄로 단계·상태·errno·예상/수신/전달 본문 바이트를 기록한다. 원래 헤더·본문·사용자 문자열을 출력하지 않는다.

## 검증과 완료 기준

아래는 앞으로 수행할 검증 계획이며 실행 결과가 아니다.

- 단위 검증: 설정 오류·중복·예약 영역, 요소 경계·가장 긴 접두사, 상태·헤더·길이 검증, 헤더 제거와 반복 헤더 보존.
- TCP 통합 검증: 두 백엔드 라우팅, 경로·쿼리·Host 유지, GET·POST·바이너리 본문, 미매칭 정적·CGI, `/` 규칙과 CGI 예약.
- 경계 검증: 분할 헤더·본문, 길이 0, 204·304, 중복 길이·오버플로·Transfer-Encoding·1xx·길이 누락, 헤더 32KiB 경계.
- 수명·실패 검증: 연결 거절, 각 시간 제한, 조기 EOF, 클라이언트 끊김, 느린 클라이언트의 역압, 전송 후 오류 응답 미추가, fd·자식 회수.
- 클라이언트 keep-alive에서 요청별 백엔드 연결이 새로 생성되고 닫히는지 확인한다.
- 기존 정적 파일·CGI 테스트와 sanitizer를 실행해 회귀와 메모리 오류를 확인한다.
- curl·브라우저로 기능을 확인하고, 일반 빌드에서 동시 요청 부하와 실행 조건을 기록한다. 처리량 수치 목표는 아직 정하지 않았다.
